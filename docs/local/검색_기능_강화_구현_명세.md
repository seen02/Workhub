# 검색 기능 강화 구현 명세

작성일: 2026-09-30  
상태: 2026-09-30 로컬 구현·핵심 실행 검증 완료. 전체 타입 검사·운영 부하 인수는 미완료이며 [구현·검증 결과](검색_기능_강화_구현_검증_결과.md)에 구분했다.  
상위 명세: [기능 개편 구현 명세 1–4의 2번](기능_개편_구현_명세_1-4.md#2-outline-검색-기능-강화)  
대상: 이 저장소에서 구현·검증할 개발자 및 AI 에이전트.

## 1. 목표와 확정 사항

직원은 기존 Outline 검색 화면에서 문서를 찾고, 필요하면 같은 화면에서 근거 기반 답변을 받는다. Rocket.Chat에서는 기존 통합 업무 비서를 멘션해 필요한 문서 링크를 받는다. 두 진입점은 하나의 검색 서비스·색인·대상 설정·사용자 권한 체계를 공유한다.

핵심 가치 검증은 프로젝트 A에 남긴 해결 기록을 프로젝트 B의 직원이 찾아 재사용하는 것이다. 단순 재질문이나 문서 제목 검색만으로 전체 기능 완료를 판단하지 않는다.

확정한 제품 동작:

1. Outline 기존 검색창·검색 결과를 유지하며 필터 아래, 첫 결과 위에 `AI 검색` 버튼을 강조해 배치한다. 별도 메뉴를 필수 진입점으로 만들지 않는다.
2. AI 검색은 버튼을 눌러 실행한다. 입력할 때마다 실행하거나 질문처럼 보인다는 이유로 자동 실행하지 않는다.
3. 답변·근거 문서·후속 질문은 같은 검색 화면 안에 표시한다.
4. Rocket.Chat은 새 봇을 만들지 않고 기존 통합 업무 비서를 사용한다. 봇이 참여한 채널·토론방에서 실제 멘션을 받았을 때 검색한다.
5. 링크 요청에는 제목·링크를 우선 제공한다. 내용 질문·요약 요청에만 필요한 답변 생성을 수행한다.
6. 업무 보고는 기존 개인 대화방 흐름을 유지한다. 이번 작업에서 채널 보고·문서 작성 기능을 추가하지 않는다.
7. 자동 대상 등록·갱신, 공용 지식 포함 설정, 권한·최신성·시점 정확도는 이번 검색 강화의 필수 범위다.

`integrations/outline/README.md`, `upstream.lock.json`, 현재 패치와 실행 이미지를 확인한다. 현재 브랜치·미커밋 변경·배포 차이를 기록하고 다른 작업을 덮어쓰지 않는다. 구형 상위 문서의 ‘3번 미착수’ 표기를 근거로 이미 있는 프로젝트 관리 기능을 재구현하지 않는다.

공식 Outline AI Answers의 활성화나 유료 기능 변경이 아니라 자체 검색 연결을 구현한다. 기존 라이선스·고지는 보존한다. 프로젝트 관리 전용 관리자 검사나 활성화 플래그를 일반 직원의 검색 조건으로 그대로 복사하지 않는다.

## 3. Outline 화면과 사용 흐름

### 3.1 일반 검색 유지

- 검색창, 최근 검색, 제목/본문 검색, 컬렉션·문서·작성자·기간·상태 필터, 정렬, 페이지 조회, 원문 열기를 유지한다.
- 일반 검색 요청과 AI 요청의 로딩·실패 상태를 분리한다. AI가 느리거나 실패해도 문서 목록을 볼 수 있다.
- 일반 검색 결과를 RAG 등록 문서만으로 제한하지 않는다. 기존 일반 검색 대상과 AI 검색 대상은 다를 수 있다.
- 빈 검색 화면에서는 입력을 안내하고 AI 실행을 비활성화한다. 일반 검색 결과가 0개여도 의미 검색은 가능하므로 AI 버튼을 숨기지 않는다.

### 3.2 AI 검색 버튼

위치: 검색창·필터 아래, 첫 문서 결과 위. 긴 안내 문구 없이 `AI 검색` 버튼을 눈에 띄게 배치한다.

표시 예:

> **[✨ AI 검색]**

- 버튼 이름은 `AI 검색`으로 통일한다. 파란색 채움과 대비가 충분한 흰색 글자로 강조하고, 아이콘만으로 기능을 표시하지 않는다.
- `관련 문서에서 정리해 드려요` 같은 요약 서비스 안내나 검색어를 반복하는 설명 문구는 넣지 않는다. 현재 입력한 검색어로 RAG 검색을 실행하는 버튼임을 명확히 한다.
- 모바일에서도 버튼 글자와 누를 영역이 충분히 보이게 하되 문서 목록을 지나치게 밀어내지 않는다.
- 내부 검색 방식·모델·문서 ID·점수·hybrid 등은 일반 화면에 표시하지 않는다.

### 3.3 클릭 이후

1. 현재 검색어·범위·필터를 고정해 요청하고 중복 클릭을 막는다.
2. 같은 영역에 `AI 검색 중…`를 표시한다. 실제 단계와 다른 성공 안내나 가짜 진행률을 표시하지 않는다.
3. 답변이 준비되면 안내 영역을 답변·근거 링크로 교체한다. 기존 문서 목록은 아래에 남긴다.
4. 짧은 검색어는 관련 내용을 요약한다. `개발 환경`만 보고 특정 프로젝트·운영체제를 임의 지정하지 않는다. 구분이 필요하면 후보를 제시한다.
5. 질문형 입력에는 근거로 확인되는 답만 제공한다. 조건·버전·시점 차이와 기록 충돌을 필요한 만큼 설명한다.
6. 근거에는 실제 제목·컬렉션·필요한 짧은 발췌를 제공한다. 저장된 정식 문서 URL을 사용하고 AI가 URL을 만들어내지 않게 한다.
7. 답변 아래에 후속 질문 입력을 둔다. 원 질문·허용 범위·대화 문맥을 이어받되 매 질문마다 현재 권한과 근거를 다시 확인한다.

정렬 변경만으로 AI를 재호출하지 않는다. 검색어 또는 검색 범위·필터가 바뀌면 진행 중 요청을 취소/무효화하고 답변·후속 문맥을 초기화한다. 늦게 도착한 이전 결과가 새 질문에 붙지 않도록 요청 ID와 질의 지문을 검사한다. 중단이 모델 실행까지 즉시 전파되지 않더라도 표시와 후속 처리는 차단한다.

빠른 검색 팝업은 기존 문서 이동을 유지한다. 필요하면 같은 입력으로 전체 검색 화면을 여는 `AI 검색` 항목을 추가하되, 이번 필수 UI는 전체 검색 결과 화면이다. 팝업 자체에 별도 대화 앱을 만들지 않는다.

### 3.4 범위·필터 처리

- 기본 AI 범위는 `내가 볼 수 있는 검색 대상 전체`. 특정 컬렉션·문서 선택 시 그 범위의 교집합으로 좁힌다.
- 공용 지식은 프로젝트 등록 없이 검색 대상이 될 수 있다.
- 기존 검색에서 선택한 필터를 조용히 무시하지 않는다. 필터별 의미·지원 여부를 표로 구현 결과에 기록한다.
- 컬렉션·문서 제한은 필수 지원한다. 작성자·기간은 기존 검색이 사용하는 필드 의미를 확인해 일치시킨다. 문서 수정일 필터와 본문에 적힌 보고 날짜는 별개다.
- `제목에서만 찾기`는 후보 제목을 제한하고, 선택된 후보의 본문을 답변 근거로 읽을 수 있다. 이 동작을 안내한다.
- 초안·보관 문서는 기본 AI 색인에서 제외한다. 해당 상태만 선택했거나 필터를 정확히 적용할 수 없으면 이유와 필터 변경 방법을 실행 전에 안내한다. 혼합 상태에서 일부만 지원할 때도 실제 범위를 명시하며 사용자의 확인 없이 확대하지 않는다.
- 일반 검색에는 나오지만 AI 대상이 아닌 문서는 `AI 검색 대상에 포함되지 않았어요.`로 안내한다. 관리자에게만 포함 설정으로 가는 경로를 제공한다.

### 3.5 상태와 기록

| 상태 | 사용자 안내·동작 |
|---|---|
| 실행 전 | 강조된 `AI 검색` 버튼 |
| 검색/답변 중 | 실제 처리 단계의 짧은 문구, 중단 가능 |
| 성공 | 답변·근거·후속 질문 |
| 근거 부족 | `선택한 범위에서 답변 근거를 찾지 못했어요.` |
| 검색 준비 중 | `문서를 검색할 수 있도록 준비하고 있어요.` |
| 일부 자료 조회 실패 | 불완전함을 알리고 확인한 근거만 답하거나 재시도 안내 |
| 서비스 실패 | `지금은 답변을 가져오지 못했어요. 다시 시도해 주세요.` 일반 검색 유지 |
| 권한 변경 | 해당 답변·근거를 더 이상 제공하지 않고 재검색 안내 |

초기 버전의 Outline AI 대화는 현재 화면 세션에 한정한다. 새로고침 후 일반 검색어·필터는 기존 동작을 따르며, AI 답변·후속 대화의 영구 복원은 필수가 아니다. 민감한 답변을 localStorage나 공유 검색 URL에 저장하지 않는다. 보존 정책을 추가하려면 사용자별 저장·현재 권한 재검사를 함께 설계한다.

## 4. Rocket.Chat 멘션 검색

### 4.1 입력과 라우팅

대표 입력: `@통합 업무 비서 프로젝트 A 설계 문서 링크 제공해줘`

- 표시 이름 문자열만으로 멘션 여부를 판단하지 않는다. Rocket.Chat의 실제 봇 사용자 ID와 멘션 메타데이터/현재 버전의 검증된 이벤트 형식을 사용한다.
- 봇이 참여한 허용 채널·토론방만 구독한다. 타인의 개인 대화방이나 전체 회사 대화를 임의 수집하지 않는다. 멤버십·퇴장·보관 변경 시 구독을 갱신한다.
- 봇 자신·시스템 메시지·멘션 없는 채널 대화에는 검색 응답을 생성하지 않는다. 인용문에 보이는 이름이나 비슷한 표시 이름도 멘션으로 처리하지 않는다.
- 채널 멘션은 검색 경로에서 처리하고 기존 자유 입력 보고 경로로 흘려보내지 않는다. 채널에서 보고를 요청하면 개인 대화방 이용을 안내한다.
- 개인 대화방의 기존 보고·버튼·취소를 보존한다. 기존 `자료 <질문>` 검색은 호환하며 명확한 문서 찾기 요청은 검색으로 분기한다. 보고/검색 의도가 애매하면 한 번 확인하며 자동 쓰기는 하지 않는다.
- 프로젝트명을 명시하면 접근 가능한 컬렉션에서 찾는다. 명시하지 않으면 접근 가능한 검색 대상 전체를 사용한다. 마지막 보고 프로젝트나 다른 사람의 채널 질문을 검색 문맥으로 재사용하지 않는다.

### 4.2 링크 우선 응답

| 요청 | 처리·출력 |
|---|---|
| `프로젝트 A 설계 문서 링크 줘` | 프로젝트·제목/키워드 검색 우선. 충분하면 생성 모델 없이 정식 링크 반환 |
| `지난번 배포 오류 해결한 문서 찾아줘` | 키워드·의미 검색으로 관련 근거 탐색, 짧은 문서 목록 |
| `프로젝트 A 설계 내용 요약해줘` | 접근 가능한 본문을 읽고 요약·출처 반환 |
| `DB 연결 오류 어떻게 해결했어?` | RAG 답변·조건·근거 링크 |
| 동명 프로젝트 또는 구분이 필요한 문서 | 접근 가능한 후보를 선택하도록 안내 |
| 기록 없음/준비 중/실패 | 각 상태를 구분하며 링크를 지어내지 않음 |

기본 링크 목록은 상위 3건 이내와 문서별 필요 시 한 줄 설명으로 제한한다. 설명은 실제 메타데이터·발췌를 사용하며 링크 요청 때문에 긴 요약 생성을 강제하지 않는다. 후보 선택에는 사용자·방·요청·만료 정보를 묶어 다른 사용자의 클릭이나 오래된 선택을 거부한다. 선택 후 권한을 다시 확인한다.

### 4.3 응답 위치와 공개 범위

- 공개 가능한 결과는 원 질문의 스레드로 답한다. 이미 스레드 안에서 요청했다면 그 스레드를 유지한다. 토론방 ID와 스레드 부모 메시지 ID를 구분한다.
- 요청자의 Outline 열람 권한과 채널에 공개해도 되는지를 별도로 판정한다. 채널의 현재 멤버 몇 명을 확인한 것만으로 공개 허용으로 간주하지 않는다. 공개 채널은 향후 참여자도 기록을 읽을 수 있다.
- 초기 정책은 `검증된 회사 공통 공개 범위` 또는 명시적인 채널–컬렉션 공유 정책이 있는 자료만 채널에 제목·링크·요약을 게시한다. 정책 기능이 아직 없거나 대상 문서가 예외 권한이면 개인 대화로 전달한다. 프로젝트 이름이 같다는 이유로 채널 공개를 허용하지 않는다.
- 개인 대화 전환 시 채널에는 문서 제목·존재·발췌를 노출하지 않고 `검색 결과는 개인 대화방으로 안내했어요.`만 표시한다. 실제 개인 대화 전송 성공 후에만 이 문구를 보낸다. 실패하면 문서 정보 없이 개인 대화방에서 다시 요청하도록 안내한다.
- 요청자에게도 권한이 없는 문서는 개인 대화에서도 제공하지 않는다. 후보·모델 입력·최종 응답 모두 같은 원칙을 적용한다.
- 검색 결과 채팅은 정상 저장 API로 전송한다. 새로고침·재로그인·다른 허용 사용자에서 보존을 확인하며 임시 이벤트 메시지만으로 완료 처리하지 않는다.
- 이미 공유한 채팅 정보는 이후 Outline 권한 철회만으로 회수되지 않는다. 따라서 채널 공유 정책을 보수적으로 적용하고, 문서 원문 열기는 항상 현재 Outline 권한에 맡긴다. 과거 메시지 자동 삭제는 이번 범위가 아니다.

### 4.4 중복·재시작·대기

- 원 요청 메시지 ID와 동작 종류로 중복을 방지한다. 전송 성공 메시지 ID를 저장하고 응답 유실 시 확인 후 재전송한다. 단순 무조건 재시도로 답변을 중복 게시하지 않는다.
- 재연결 시 처리 완료한 멘션을 재실행하지 않는다. 복구 범위·보존 기간을 명시하고 제한된 미처리 구간만 재조회한다. 메시지 수정으로 자동 재검색하지 않고 새 요청을 안내한다.
- 멘션 검색은 보고 작업과 분리된 제한된 대기열/실행 경로를 사용한다. 공용 모델 자원이 포화되면 실제 대기 상태를 알린다. 무제한 동시 실행으로 보고를 느리게 하지 않는다.
- 짧은 후속 질문을 지원할 경우 `(사용자, 방, 스레드)`별 검색 문맥만 사용하고 다른 사람의 개인 결과를 섞지 않는다. 초기 필수 범위는 멘션을 포함한 독립 검색과 후보 선택이며 자연스러운 다중 사용자 토론 이해는 제외한다.

## 5. 공통 검색 서비스와 데이터 계약

화면마다 새 색인·별도 검색 엔진을 만들지 않는다. 기존 RAG와 일반 문서 조회를 공통 읽기 전용 서비스로 묶는다. 기존 보고용 업무 후보 탐색과 지식 검색은 범위와 응답 계약을 구분한다.

요청의 논리 필드(실제 API 이름은 기존 구조에 맞추되 검증 시 문서화):

| 필드 | 규칙 |
|---|---|
| `request_id` | 중복·추적·취소 식별. 신원 증명으로 쓰지 않음 |
| `query` | 길이 제한·빈 값 검증, 표시 시 이스케이프 |
| `mode` | `links`, `answer`; 서버가 허용된 읽기 동작만 실행 |
| `scope`, `filters` | 컬렉션/문서 ID와 지원 필터. 서버가 권한·포함 여부 확인 |
| `conversation_id` | 사용자·진입점별 후속 질문 문맥. 다른 사용자의 ID 거부 |
| `origin` | Outline/채팅, 채팅이면 방·스레드·원 메시지 ID를 서버에서 검증 |
| 사용자 정보 | Outline 세션 또는 실제 Rocket.Chat 발신자로부터 서버에서 결정. 브라우저가 보낸 이메일/역할을 신뢰하지 않음 |

응답은 `status`, `request_id`, `mode`, `effective_scope`, `documents`, `answer`, `citations`, `warnings`를 분리한다. 준비 중·진행·완료·후보 선택 필요·근거 없음·실패·취소를 HTTP 성공 여부와 별도로 나타낸다. 문서에는 검증된 ID·URL·제목·컬렉션·revision·필요한 발췌를 연결한다. 사용자 화면에는 내부 필드를 직접 출력하지 않는다.

처리 순서:

1. 현재 사용자 확인 → 범위·공개 정책 확정.
2. 프로젝트/문서 명시 여부 해석 → 동명 대상이면 확인.
3. 링크 요청의 명확한 제목·키워드 일치 탐색 → 충분하지 않으면 의미 검색 병행.
4. 답변 요청은 제목/키워드/의미 검색을 결합해 후보를 찾고 관련 부분을 선택한다. 일반 검색 상위 몇 건만 그대로 요약하는 것으로 RAG 구현을 대체하지 않는다.
5. 후보의 현재 원문·권한·revision 확인 → 필요한 근거만 모델에 전달.
6. 답변의 주요 주장과 실제 근거 연결 → 전송 직전 권한·공개 범위·삭제·최신성 재확인.
7. 오래된 근거면 최신 원문으로 제한적으로 재검색/재생성하고 반복 변경 시 재시도를 안내한다. 이전 내용과 최신 출처를 섞지 않는다.

링크 검색도 실제 인덱스·API 범위를 확인하고 표시한다. 이번 기본 봇 범위는 활성 검색 대상 컬렉션이다. 일반 Outline 검색이 더 넓다고 해서 서비스 계정 전체 문서를 봇에 노출하지 않는다.

동기 응답을 유지할지 기존 문서 에이전트 작업 제출/조회 방식을 재사용할지는 현재 지연·취소 지원을 확인해 결정한다. 긴 처리는 요청 접수와 최종 결과를 구분하고 요청 ID로 추적한다. UI·봇이 HTTP 연결을 오래 붙잡아야만 동작하는 구조를 피한다.

## 6. 검색 대상 자동 관리

관리 UI는 현재 Outline 관리 연동을 활용해 관리자 설정의 `AI 검색 대상` 또는 컬렉션 설정으로 제공한다. 직원에게 별도 Workhub 등록 절차를 요구하지 않는다. 관리자 여부와 컬렉션 접근 권한을 모두 확인한다.

| 상황 | 필수 동작 |
|---|---|
| 프로젝트 연결(Outline 관리 UI 포함) | 검색 포함 사유 추가, 초기 색인 예약 |
| 연결된 프로젝트의 업무·문서 생성/수정 | 변경 문서 자동 갱신 |
| 보고에서 새 업무 생성 | 즉시 업무 탐색 가능, RAG 갱신 예약. 두 완료 시점 구분 |
| 새 Outline 컬렉션 | 관리 목록 자동 발견. 발견만으로 포함하지 않음 |
| 지식 컬렉션 | 관리자 `AI 검색에 포함`으로 등록. 업무 프로젝트 등록 불필요 |
| 프로젝트 연결 해제 | 독립 지식 포함 설정이 있으면 검색 유지 |
| 마지막 포함 사유 제거 | 즉시 질의 대상 제외, 잔여 색인 정리. 원문 유지 |
| 문서 삭제·보관·이동·권한 변경 | 현재 질의에서 제외/범위 재평가, 비동기 색인 정리 |

컬렉션 ID와 독립 포함 사유를 원본으로 관리한다. 이름 변경·동명 컬렉션·기존 환경 설정 이전 시 중복 등록하지 않는다. 관리 UI와 환경변수가 서로 다른 포함 정책을 유지하지 않도록 이전 절차를 정한다.

Workhub의 쓰기 성공은 갱신을 바로 예약한다. Outline 직접 수정은 주기 비교로 감지하고, 검증된 이벤트 연동이 있으면 가속 수단으로 사용한다. 정기 대조는 이벤트 누락 복구를 위해 유지한다. 페이지 끝까지 성공적으로 읽은 목록만 삭제 대조에 사용한다.

문서 ID·revision/내용 해시로 부분 갱신하고 불변 문서를 매번 재임베딩하지 않는다. 갱신 중 새 변경·동시 작업·재시작에도 작업이 유실되지 않도록 저장된 작업 상태와 재시도를 사용한다. 권한 변경은 색인 완료를 기다리지 않고 질의 시 차단한다.

관리 화면은 `미포함 / 검색 준비 중 / 사용 가능 / 갱신 중 / 일부 실패`, 마지막 성공 시간·문서 수·실패 수·재시도 기능을 제공한다. 담당 개발자에게 설정 파일 수정을 요청해야만 복구되는 구조를 만들지 않는다.

## 7. 검색 정확도·권한·성능

### 7.1 정확도

- 프로젝트·문서 제목·보고 날짜·시각·업무 항목·완료 기준을 묶어 분할한다. 일반 텍스트의 날짜·시각도 처리한다.
- 현재 본문·보고 이력·인용·템플릿 예시를 구분한다. 예시의 완료 상태를 실제 상태로 답하지 않는다.
- 현재 상태는 최신 원문, 과거 질문은 해당 시점의 기록을 사용한다. 문서 최종 수정일을 보고 발생 시각으로 대체하지 않는다.
- 정확한 제목, 일부 단어, 표현이 다른 질문, 오류 문자열, 여러 프로젝트·문서를 함께 묻는 경우를 평가한다.
- 기록이 충돌하면 충돌을 표시한다. 조건이 다른 해결 사례를 현재 문제의 확정 해법으로 말하지 않는다.
- 답변의 주요 사실에 관련 근거를 붙인다. 불필요한 출처를 늘리거나 실제 없는 URL·문서 제목을 생성하지 않는다.
- 문서 내용은 근거 자료이며 실행 지시가 아니다. 문서 안의 명령으로 권한·도구 동작·시스템 규칙을 변경하지 않는다.

### 7.2 권한과 데이터 노출

서버에서 확인한 사용자 신원을 기존 서명 연결·사용자 ACL에 전달한다. 후보 검색·본문 읽기·모델 입력·최종 답변과 출처에 모두 권한을 적용한다. 서비스 계정의 관리자 권한을 요청자의 권한으로 취급하지 않는다. 확인 실패는 허용으로 처리하지 않는다.

신규 검색 경로는 일반 직원의 읽기 권한으로 동작하고 관리자 전용 설정과 분리한다. 기존 Outline 로그인 검증·CSRF 정책을 따른다. 서버 토큰·서명키를 브라우저나 봇 응답에 넣지 않는다. 렌더링은 안전한 Markdown과 허용된 문서 URL을 사용한다.

사용자별 응답·후속 대화 캐시는 범위·필터·문서 버전·권한을 고려하고 재사용 전 현재 권한을 확인한다. 권한 철회 전에 만든 답변을 다른 사용자에게 재사용하지 않는다. 로그에는 단계·시간·요청 ID·오류 분류를 우선 남기고 비밀키나 전체 민감 본문을 기록하지 않는다.

### 7.3 성능과 측정

- 링크 요청은 가능한 경우 생성 모델 호출 0회를 목표로 한다. 임베딩 호출과 답변 생성 호출을 구분해 기록한다.
- 요청 내 중복 사용자·권한·원문 조회를 줄이고 기존 연결 재사용을 활용한다. 저장된 캐시로 최종 권한 검사를 생략하지 않는다.
- 기존 업무 보고의 큐·취소·확정 응답을 검색 작업이 막지 않게 한다. 동시에 생성 가능한 수는 실제 모델 자원에 맞춰 제한한다.
- 일반 문서 결과 표시, 요청 접수, 대기, 권한 검사, 후보 검색, 원문 읽기, 모델 생성, 채팅 전송을 따로 측정한다.
- 임시 목표: 화면 접수 표시 1초 이내, 명확한 링크 검색은 준비된 환경에서 3초 내외, 일반 검색 지연은 기존 대비 20% 이상 지속 악화하지 않음. 보장 수치가 아니며 실제 환경·반복 횟수와 함께 측정하고 미달 원인을 기록한다.
- 답변 생성 목표는 구현 전 현재 장비 기준값을 측정해 정한다. p50·p95·최대값·표본 수, 첫 요청/반복 요청, 동시 사용자 조건을 구분한다. 몇 번의 시연으로 운영 성능을 보장하지 않는다.
- 컬렉션 발견, 문서 변경 감지, 색인 완료 지연도 별도로 기록한다. 자동 갱신을 즉시 최신 답변으로 표현하지 않는다.

| 빌드·복구 | `integrations/outline/README.md`, `export_patch.py`, `prepare_source.py`, `upstream.lock.json`, Docker 빌드 |

위 목록은 수정 강제가 아니라 조사 시작점이다. 구현 후 실제 변경 경로·API 계약·설정을 이 문서의 진행 기록에 남긴다. upstream 소스만 수정하고 관리 패치를 갱신하지 않은 상태로 완료 처리하지 않는다.

## 9. 구현 순서와 단계별 통과 기준

| 단계 | 작업 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| S0 | 현재 코드·배포·권한·검색 대상·질문 기준값 조사, 백업·검증 데이터 준비 | 기존 결과·지연과 실패 원인이 재현 가능 |
| S1 | 공통 읽기 검색 계약, 신원·범위·링크/답변 모드, 대상 정책·관리 설정 | 일반 직원/관리자/권한 없는 계정 범위가 정확하고 기존 보고 호환 |
| S2 | 자동 포함·발견·부분 갱신·삭제/이동·실패 복구 | 신규 문서와 수정이 수동 RAG 등록 없이 검색되며 권한 철회 즉시 차단 |
| S3 | 제목·키워드·의미 탐색, 근거·시점·최신성 개선 | 고정 필수 질문과 개발에 쓰지 않은 표현 변경 질문 통과 |
| S4 | Outline 안내·버튼·답변·출처·후속 질문·취소 통합 | 실제 브라우저에서 일반 검색과 AI 검색이 독립적으로 정상 동작 |
| S5 | Rocket.Chat 채널·토론방 멘션·링크·후보 선택·스레드·개인 안내 | 두 방 유형에서 실제 멘션과 공개 정책·보존·중복 방지 통과 |
| S6 | 통합 회귀·성능·배포 패치·복구 검증, 결과 보고 | 아래 필수 검증 완료, 미해결 사항을 구분해 기록 |

기존 동작이 충족되면 재구현하지 않고 검증 근거를 남긴다. 큰 변경을 한꺼번에 배포하지 않고 단계별 테스트를 통과시킨다. 화면만 완성한 것을 검색 강화 완료로 표시하지 않는다.

## 10. 테스트와 완료 기준

### 10.1 검증 데이터와 계정

전용 검증 컬렉션·문서·채널·토론방을 사용한다. 관리자, 일반 직원 A, 다른 프로젝트 직원 B, 권한 없는 계정으로 검증한다. 실제 사용자 비밀번호·토큰은 결과 문서에 기록하지 않는다.

검증용 프로젝트 A/B, 독립 공용 지식 컬렉션, 비공개 컬렉션, 동명 문서, 오전/오후 보고, 충돌 기록, 예시 템플릿, DB 오류 해결 사례를 준비한다. 오류 해결 사례는 검증용이라고 표시하고 실제 사건처럼 설명하지 않는다. 4번 대화 문서화 없이 수동으로 준비한다.

각 질문에 사용자·범위·기대 사실·허용 출처·금지 내용·기대 링크를 고정한다. 실제 모델 출력은 근거와 비교하고 HTTP 200만으로 성공 판정하지 않는다.

### 10.3 실제 화면 시연

Outline: 일반 직원 B 로그인 → 기존 검색창에 오류 증상 입력 → 일반 문서 목록 확인 → `AI 검색` → A의 공유 해결 기록에 근거한 답변 → 원문 열기 → 조건을 좁혀 후속 질문.

Rocket.Chat: 검증 채널에서 봇 실제 멘션 → `프로젝트 A 설계 문서 링크 제공해줘` → 스레드의 제목·링크 확인 → 클릭해 Outline 원문 확인 → 토론방에서도 반복 → 새로고침과 다른 허용 계정으로 보존 확인. 별도로 비공개 자료의 개인 안내와 동명 문서 선택을 검증한다.

자동 관리: 새 컬렉션 발견 → 지식 검색 포함 → 초기 색인 → 문서 수정 → 자동 갱신 → 검색 → 직원 권한 철회 → 제목/내용 차단. 프로젝트 연결 해제 후 독립 지식 포함이 유지되는 경우도 확인한다.

실제 화면·실제 모델·실제 전송의 검증과 단위/모의 테스트를 구분해 기록한다. 사용자 원문과 기존 업무 상태를 테스트 때문에 바꾸지 않는다. 전용 데이터와 설정은 전후 목록·스냅샷으로 확인해 정리하고 기존 데이터 보존을 검증한다.

## 11. 배포·복구와 결과 보고

- 코드 변경 전 현재 Outline/Workhub/문서 에이전트 이미지·설정·검색 정책 저장소·필요 DB의 복구 지점을 기록한다. 비밀값은 보고서에 남기지 않는다.
- 새 검색 진입점과 멘션 수신을 따로 비활성화할 수 있게 한다. 복구 시 일반 검색과 개인 대화방 보고가 유지되어야 한다.
- 스키마 변경은 가능한 추가형으로 하고 데이터 이전·이전 코드 호환 여부를 검증한다. 새 업무가 추가된 DB를 오래된 전체 백업으로 무조건 덮어쓰지 않는다.
- Outline 관리 패치 내보내기·원본에서 재적용·빌드를 검증한다. 로컬 적용과 배포 패키지 반영 여부를 구분해 기록한다.
- 변경 기능, 실제 테스트 결과, 미통과/제한, 단계별 성능, 일반 직원의 테스트 절차, 사용 가능한 화면·방, 복구 방법을 최종 보고한다.
- 모든 필수 항목이 통과한 경우에만 전체 완료로 표시한다. 특정 필터 미지원 등 허용한 제한도 제품 안내·테스트·최종 보고에 일치하게 명시한다.

## 12. 제외 범위

첨부 OCR·이미지 이해·모든 파일 형식 검색, Rocket.Chat 과거 대화 전체 색인, 4번 대화 기반 문서 생성, 검색 중 업무/문서 자동 수정, 새 봇 계정 신설, Outline 공식 유료 AI 기능 활성화, 장비 교체는 이번 구현에 포함하지 않는다. 필요하면 별도 요청으로 진행한다.
