# 프로젝트별 업무 목록 문서 구조

2026-09-18 적용. 허브와 Rocket.Chat에서 등록한 새 업무는 선택한 컬렉션의 최상위 **업무 목록** 문서 아래에 생성된다. 프로젝트 자료는 기존 위치에 유지한다.

```text
프로젝트 A [컬렉션]
├─ 업무 목록
│  └─ A-1
├─ 프로젝트 개요
├─ 요구사항 문서
│  ├─ 하위 문서 1
│  └─ 하위 문서 2
├─ 일정
├─ 회의록
└─ 관리자 전용 파일
```

업무 목록은 폴더 역할의 일반 문서다. Outline에서 펼치면 하위 업무가 보이며, 문서 본문 아래에도 하위 문서 링크가 표시된다. 허브와 봇에서는 중간 문서를 선택할 필요 없이 기존처럼 프로젝트 → 업무를 선택한다.

## 적용 범위

| 프로젝트 | 이동한 업무 수 |
|---|---:|
| 통합 업무 | 5 |
| 시연 · 고객 포털 | 1 |
| 시연 · 문서 자동화 | 1 |
| 팀 협업 시연 | 1 |
| 프로젝트 A | 1 |
| 합계 | 9 |

기존 업무의 ID·URL·제목·본문·담당자·완료 기준·보고 이력을 보존하고 상위 문서 위치만 변경했다. 일반 프로젝트 문서의 본문·위치·버전·수정 시각이 그대로인지 비교했다. 허브에 연결하지 않은 컬렉션은 대상에서 제외했다.

문서 이동으로 Outline 버전은 1씩 증가했다. 따라서 **이동 전에 만든 미확정 초안은 원본 버전 충돌로 확정이 차단될 수 있다. 취소하고 새로 보고한다.** 이미 확정한 보고와 현재 업무 상태는 유지된다.

## 구현

- `src/workhub/outline.py`의 `task_parent()`가 프로젝트별 상위 문서를 준비한다. 최초 업무 등록 시 최상위에 같은 이름의 일반 문서가 하나 있으면 사용하고, 없으면 새로 생성한다. 동명 문서가 여러 개이거나 해당 문서 자체가 업무 양식이면 임의로 선택하지 않고 안내한다.
- `task-parent:<collection ID>` 키에 상위 문서 ID를 보관한다. 생성 요청 전에 ID를 예약해 응답 유실 후 재시도에도 중복 생성을 방지한다. 확정된 ID는 문서 목록 검색 대신 `documents.info`로 직접 확인하므로 이름 변경과 목록 조회 지연의 영향을 줄인다.
- 공통 업무 생성 함수가 `documents.create`에 `parentDocumentId`를 추가한다. 허브의 등록 화면과 봇의 `작성` 명령이 같은 함수를 사용한다.
- 업무 동기화는 컬렉션 전체의 문서를 조회하므로 하위 업무도 계속 수집한다. 일반 상위 문서는 업무 양식이 없어 업무 건수·완료 기준 통계에 포함하지 않는다. 자료 검색 범위는 기존 프로젝트 컬렉션으로 유지한다.
- 삭제·보관되었거나 다른 컬렉션으로 이동한 상위 문서에는 새 업무를 생성하지 않는다. 기존 상위 문서를 Outline에서 복원해야 한다. 저장된 문서를 다른 문서 밑으로 옮긴 경우에도 원래 최상위 위치로 되돌려야 한다.
- 일반 동기화에서 문서를 자동으로 이동시키지는 않는다. 기존 업무 정리는 명시적으로 실행하는 `src/workhub/organize_tasks.py`가 맡는다. 현재 단일 workhub 프로세스 구성에서 생성은 기존 잠금으로 직렬화한다.

## 직접 확인

1. [프로젝트 A의 업무 목록](http://192.0.2.20:8090/doc/example-document)을 연다. **A-1**이 하위에 있고 요구사항·회의록 등은 기존 위치에 있는지 확인한다.
2. [업무 허브](http://localhost:8004)에서 프로젝트를 선택하고 **업무 등록**한다. Outline의 같은 업무 목록 아래에 새 문서가 생기는지 확인한다.
3. Rocket.Chat에서 **시작 → 프로젝트 → 업무**를 선택하고 보고한다. 초안을 확정하면 해당 하위 문서의 완료 기준과 진행률이 바뀐다. 취소하면 원본은 유지된다.
4. 팀장은 진행 통계에서 업무·완료 기준 통계를 확인한다. 업무 목록과 PRD 같은 일반 문서는 업무 건수에서 제외된다.

## 검증 자료

최종 배포 버전의 자동 테스트 **64개 통과**, 실제 Authentik 관리자·실무자와 브라우저를 사용한 통합 검증 **21개 통과**. 실제 Outline 화면에서 상위 문서와 하위 업무 표시도 확인했다. 테스트 컬렉션을 제거한 뒤 기존 업무 9개의 본문·부모 연결이 검증 전과 같음을 확인했다.

- 자동 회귀 테스트: `reports/hierarchy-unit-tests.txt`.
- 실제 계정·브라우저 검증: `reports/hierarchy-verification.json`. 별도 검증 컬렉션에서 새 상위 문서 생성, 중복 요청, 이름 변경 후 포털 등록, 봇의 선택·기존 양식 보고·확정·체크리스트·통계·취소·업무 등록을 검사한다. 검증 컬렉션은 종료 후 제거하며 기존 업무 본문과 상위 연결이 그대로인지 확인한다.
- 기존 문서 이동 결과: `reports/hierarchy-migration.json`.
- 화면: `reports/hierarchy-outline.png`, `reports/hierarchy-portal.png`, `reports/hierarchy-chat.png`.

## 백업과 재실행

실제 변경 직전의 문서 스냅샷과 SQLite 백업:

`runtime/workhub/hierarchy-backups/00000000-0000-4000-8000-000000000001/`

`before.json`은 프로젝트별 원문과 이전 부모 ID, `workhub.sqlite3`는 비서 DB, `result.json`은 이동 기록이다. 백업에는 계정 세션과 업무 원문이 포함되므로 기존 runtime 비공개 보관 방침을 적용한다.

계층 정리는 이미 완료했다. 필요할 때만 먼저 읽기 전용 계획을 확인한다.

```powershell
docker compose exec -T workhub python -m workhub.organize_tasks
```

적용은 쓰기 작업과 겹치지 않도록 workhub를 정지한 상태에서 실행하고, 성공 여부와 관계없이 다시 시작한다. 이미 지정된 상위에 있는 업무는 다시 이동하지 않는다.

```powershell
docker compose stop workhub
try {
  docker compose run --rm --no-deps workhub python -m workhub.organize_tasks --apply
} finally {
  docker compose up -d --no-deps workhub
}
```

되돌려야 한다면 백업의 문서 ID와 이전 `parentDocumentId`를 기준으로 Outline 문서 이동을 사용한다. 문서 자체를 복제하거나 과거 DB를 그대로 덮어써서 그 이후 보고를 잃지 않도록 한다. 이동 후에는 새 초안을 작성하고 동기화한다.
