# Rocket.Chat 보고 성능 및 신뢰성 개선 명세

작성일: 2026-09-30  
상태: 1단계 완료. 2026-10-07 2단계 중 명확한 보고의 직접 해석을 구현·검증하고 로컬 실행 서비스에 적용했다. 업무 목록 사전 갱신과 3~5단계는 미착수.  
목적: 현재 보고 흐름의 중복 조회와 불필요한 AI 호출을 줄이고, 접수·저장 결과를 명확하게 표시한다.

## 1. 작업 범위와 진행 원칙

기본 흐름은 유지한다.

> 통합 업무 비서 개인 대화방에 여러 업무 보고 → 초안 확인 → 보고 및 반영 → 채널 선택 → 채팅 게시와 Outline 저장 → 결과 확인

- 보고 양식의 업무 목록에는 업무 문서명, 각 업무의 번호에는 완료 기준을 표시한다.
- 여러 프로젝트·여러 업무, 기존 업무 수정, 없는 본인 업무 생성, 초안 수정, 뒤로 가기와 재시도를 유지한다.
- 보고에 없는 업무·기준을 추가하거나 언급한 업무를 조용히 누락하면 안 된다.
- 권한, 실제 문서와 기준의 식별자, 원문 버전, 중복 전송·반영 방지 검사를 유지한다.
- 이번 작업에 새 업무 기능, 모델 교체, 서버 구매·이전은 포함하지 않는다.
- 기존 [기능 개편 명세 1~4](기능_개편_구현_명세_1-4.md)와 별개의 **성능 개선 1~5단계**다. 검색 기능 전면 개편 등의 미착수 항목을 이번 작업에 임의로 포함하지 않는다.
- 아래 1 → 2 → 3 → 4 → 5 순서로 진행한다. 단계별 구현·검증·결과 기록을 마친 뒤 다음 단계로 넘어간다. 사용자가 특정 단계만 요청하면 해당 단계까지만 수행한다.
- 완료 기록은 이 문서 마지막에 누적한다. 단계마다 별도 사용 가이드나 유사한 명세를 늘리지 않는다. 측정 원자료는 JSON 등으로 따로 보관할 수 있다.

## 2. 시작점과 확인된 사항

### 과거 측정과 현재 상태를 구분한다

- 이전 측정에서는 초안 생성과 반영 전 검사 과정에서 사용자 목록을 59번 조회했다. 특정 입력·실행 시점의 결과이며 모든 보고의 고정 횟수는 아니다.
- 이전 초안 처리 시간은 측정 사례에 따라 약 56~75초였다. 입력, 모델 적재 상태, 조회 대상과 측정 구간이 달라 단일 기준값으로 사용하면 안 된다.
- 요청 내 캐시와 HTTP 연결 재사용 작업은 사용자 요청으로 중단·롤백했다. 당시 임시 테스트 결과는 현재 적용 결과로 계산하지 않는다.
- 2026-09-30 업무 인식 오류 수정은 별도로 적용됐다. 명시된 프로젝트 → 업무 → 완료 기준을 나누고 일부 명확한 표현을 AI 없이 해석하는 코드가 이미 있다.
- 다만 현재 `report_parser.plan`은 해당 해석 전에 업무 목록 조회와 RAG 후보 탐색을 수행하며, `extract_scoped` 실행 전에 LLM 잠금도 잡는다. **명확한 입력의 AI 해석 일부 생략과, RAG·불필요한 대기까지 생략하는 것은 다른 작업이다.**
- 최근 인식 수정 기록의 Workhub 자동 테스트는 242개 통과다. 이번 작업의 테스트 수·결과는 새로 실행하여 기록한다.
- 최신 수정의 실제 조회 검증에서는 초안이 약 24~42초 걸린 사례도 있었다. 과거 측정과 입력·구간을 맞추지 않은 단순 속도 비교는 하지 않는다.

근거: 보고 업무 오인식 복구 (`reports/report-task-scope-repair-20260930.md`; 로컬 자료), 보고 및 반영 통합 검증 (`reports/report-combined-validation-20260929.md`; 로컬 자료).

## 3. 성능 개선 1단계 — 단계별 측정과 요청 내 중복 조회 제거

### 구현

1. 초안 생성, 채널 선택 후 제출을 별도 요청으로 측정한다. 각 요청에 추적 ID를 부여한다.
2. 대기 시간, 업무 목록 준비, 권한·담당자 조회, RAG, AI, 실제 문서 확인, 채팅 전송, 문서 저장, 결과 안내 시간을 구분한다. API별 호출 수·캐시 적중 수·재시도 수·실제 AI 호출 수도 기록한다.
3. 한 요청 안에서 같은 사용자 목록·담당자 정보·권한 조회·문서 조회를 재사용한다. 이미 있는 `permissions.request_snapshots`의 범위와 봇 경로 적용 여부부터 확인한다.
4. 캐시 키에는 사용자 신원, 조회 대상과 결과에 영향을 주는 인자를 포함한다. 사용자별 결과를 다른 사용자에게 재사용하지 않는다. 요청 종료·실패 시 요청 문맥을 반드시 해제한다.
5. 보고 초안 생성, 채널 선택·제출, 재시도는 각각 새 요청으로 취급한다. 초안 때의 권한 캐시를 나중에 제출할 때 그대로 사용하지 않는다.
6. 실제 문서 저장 직전에는 관련 권한·담당자와 문서 버전을 새로 확인한다. 캐시 우회가 문서뿐 아니라 관련 권한 조회까지 적용되게 한다. 여러 문서 저장 중에도 문서별 충돌 검사를 유지한다.
7. 서비스별 HTTP 클라이언트를 재사용한다. 동기·비동기 호출, 스레드·이벤트 루프 경계를 확인하고, 연결 제한·시간 제한·종료 처리를 정한다. 사용자별 인증 헤더를 공유 클라이언트의 전역 상태에 덮어쓰지 않는다.
8. 조회 오류를 정상 결과처럼 캐시하지 않는다. 쓰기 응답 유실 시 무조건 재전송하지 않고 기존 반영 확인·복구 방식을 유지한다.

### 검증과 완료 기준

- 변경 전후 동일한 입력·계정·업무 문서·하드웨어·모델로 비교한다.
- 같은 요청의 동일 조회가 실제로 줄었는지 호출 수로 증명한다. 저장 직전 재확인처럼 필요한 중복은 따로 표시한다.
- 서로 다른 사용자와 연속 요청 간 캐시가 섞이지 않는지 확인한다.
- 초안 이후 권한 회수, 담당자 변경, 원문 수정, 문서 삭제·이동 시 제출이 적절히 차단되는지 확인한다.
- 실패·재시도·연결 재수립 후에도 기존 보고 전송과 Outline 반영 결과가 동일해야 한다.
- 경과 시간과 호출 수를 함께 보고한다. API 호출만 줄고 체감 시간이 그대로라면 그 사실과 남은 병목을 기록한다.

**완료:** 정확성·권한·충돌 검증을 통과하고 중복 조회 감소와 실제 소요 시간을 재현 가능한 자료로 제시한다.

## 4. 성능 개선 2단계 — 업무 목록 사전 갱신과 명확한 보고의 직접 해석

원안의 ‘전체 업무를 매번 읽지 않기’와 ‘명확하면 AI·RAG 생략하기’를 하나의 단계로 진행한다.

### 업무 목록 준비

- 기존 Workhub 업무 사본·동기화·RAG 저장 구조를 먼저 확인하고 재사용한다. 같은 목적의 별도 저장소를 중복 생성하지 않는다.
- 프로젝트 ID·이름, 업무 문서 ID·제목, 완료 기준 ID·제목, 컬렉션 ID, 원문 수정 버전, 마지막 동기화 시각·상태를 탐색에 사용할 수 있게 한다.
- 프로젝트 연결, 업무 생성·수정 뒤 해당 범위를 갱신한다. 보고로 만든 새 업무도 다음 보고에서 바로 찾을 수 있어야 한다.
- Outline에서 직접 바꾼 문서는 현재 제공되는 변경 감지 방식과 주기적 정합성 확인으로 보완한다. 동기화 실패와 마지막 성공 시각을 구분한다.
- 삭제·보관·이동·연결 해제 시 오래된 후보를 제거하거나 비활성화한다. 검색 사본을 권한의 최종 근거로 쓰지 않는다.
- 탐색 전에 현재 사용자의 접근 범위를 확인하고, 선택된 문서는 실제 원문·권한으로 재검증한다. 접근할 수 없는 후보를 모델이나 사용자에게 노출하지 않는다.
- 목록이 없거나 오래됐거나 동기화가 실패하면 관련 범위를 새로 조회한다. 필요할 때 기존 전체 조회 경로로 복구하되 실패 이유를 내부 기록에 남긴다.

### 처리 순서

> 준비된 업무 목록과 현재 접근 범위 확인 → 문장 전체 직접 해석 시도 → 필요한 경우에만 RAG·AI → 선택된 실제 문서·기준·권한 확인 → 초안

| 입력 | 처리 원칙 |
|---|---|
| “시연 프로젝트 로그인 업무의 화면 만들기 완료” | 프로젝트·업무·기준·상태가 유일하고 문장 전체가 해석되면 RAG·AI를 생략한다. |
| “로그인 화면은 끝냈어” | 업무 목록과 최근 대화에서 후보를 확인한다. 확실하지 않으면 추가 탐색·AI 또는 짧은 확인을 사용한다. |
| “지난번 인증 관련 작업 끝냈어” | RAG 후보 탐색과 AI 해석을 사용한다. 찾은 후보를 임의 확정하지 않는다. |
| “화면 만들기는 못 끝냈어” 또는 “완료할 예정이야” | ‘완료’ 문자열만 보고 완료로 처리하지 않는다. 안전하게 해석하지 못하면 직접 해석을 포기한다. |
| 여러 프로젝트·업무 또는 기존 업무와 새 업무가 섞임 | 문장 전체의 대상과 상태를 검사한다. 직접 해석한 일부만 성공한 전체 보고처럼 반환하지 않는다. |

- 기존 `literal_task_items`, 프로젝트·업무 범위 분리, 누락 검사를 재사용·보완한다.
- AI가 필요 없는 경로는 LLM 잠금을 획득하지 않는다. 모델이 사용 중이어도 명확한 보고가 모델 때문에 거부되지 않아야 한다.
- 모호한 별칭·동명이인 업무·부정·미래 표현·상태 충돌은 조용히 추정하지 않는다. 새 업무 생성 의도도 기존 업무와 구분한다.

### 검증과 완료 기준

- 명확한 입력에서 실제 AI 호출 0회, RAG 후보 API 호출 0회를 기록으로 확인한다. 권한과 선택된 원문 확인은 생략하지 않는다.
- 한 프로젝트 여러 업무, 여러 프로젝트 여러 업무, 오타·생략형, 새 업무 포함, 모호한 이름을 검증한다.
- 문서 수정·삭제·이동·권한 회수 직후 오래된 후보가 남아도 잘못된 초안·저장으로 이어지지 않아야 한다.
- 검색 서비스 장애·새 업무·동기화 실패 상황의 복구 경로를 확인한다.

**완료:** 입력 범위를 빠뜨리지 않으면서 전체 재조회와 불필요한 RAG·AI 호출을 줄이고, 최신 원문 확인을 유지한다.

## 5. 성능 개선 3단계 — AI 입력·출력 축소와 실패 부분 재해석

### 구현

- 사용자에게 허용된 관련 업무와 필요한 기준만 AI 후보에 포함한다. 입력에서 명시한 프로젝트·업무가 후보 수 제한으로 빠지지 않게 한다.
- AI는 업무·기준 선택과 상태·원문 근거 해석에 집중한다. 보고 양식, 날짜, 번호, 아이콘은 프로그램이 만든다. 이미 코드로 처리하는 부분은 새 구현으로 중복하지 않는다.
- 긴 문서 ID 대신 요청 안에서만 유효한 짧은 후보 번호를 사용한다. 응답은 서버의 고정 매핑으로 실제 ID로 변환하고, 존재하지 않거나 다른 프로젝트의 번호를 거부한다.
- 원문 근거와 누락·상태 충돌 검사에 필요한 필드는 남긴다. 토큰 절약 때문에 검증에 필요한 정보를 제거하지 않는다.
- 여러 프로젝트 중 한 부분만 실패하면 실패한 범위와 최소한의 공통 문맥만 재해석한다. 성공한 부분은 보존하되, 합친 뒤 중복·누락·권한·상태 충돌을 다시 검사한다.
- 사용자가 원문을 수정한 새 초안 버전에는 이전 원문의 성공 결과를 무조건 재사용하지 않는다.
- 재해석 횟수에 상한을 둔다. 끝내 불명확한 부분은 짧은 확인을 요청하고 일부 성공을 전체 성공으로 표시하지 않는다.

### 검증과 완료 기준

- AI 입력·출력 토큰 수, 호출 횟수, 실패 부분 재시도 횟수와 시간을 전후 비교한다.
- 후보 번호 혼동, 다른 프로젝트의 같은 업무명, 잘못된 번호, 문장 일부 누락, 기준 상태 뒤바뀜을 검증한다.
- 기존 실패 문장과 다중 프로젝트 입력의 정확도를 유지한다.

**완료:** AI가 필요한 보고의 입력·출력 또는 반복 호출 비용이 감소하고 전체 보고의 연결·상태가 유지된다.

## 6. 성능 개선 4단계 — 제출 대기 분리와 처리 상태 안내

### 구현

- 현재 `bot.consume`의 단일 처리 흐름과 보고 상태 저장 방식을 먼저 확인한다. 오래 걸리는 AI 초안 작업이 채널 선택·제출·결과 조회를 막지 않도록 실행 경로를 분리한다.
- 무제한 병렬 실행 대신 제한된 작업 수·대기열을 사용한다. 모델 추론 동시 실행 제한은 유지한다.
- 같은 보고 ID의 제출·수정·재시도는 충돌하지 않게 직렬화한다. 서로 다른 사용자·보고는 필요한 범위에서 진행할 수 있게 한다.
- 접수 안내는 실제로 요청을 수락한 뒤 표시한다. 대기열이 찼거나 접수하지 못했으면 접수된 것처럼 표시하지 않는다.
- `접수 → 사전 검사 → 채팅 전송 → 업무별 문서 저장 → 결과`를 구분한다. 안내 메시지에만 상태를 두지 말고 기존 보고 상태·중복 방지 기록에 연결한다.
- 채널 게시 권한·멤버십과 최신 문서 권한을 실행 시점에 확인한다.
- 이미 전송한 채팅이나 저장한 문서를 다시 처리하지 않는다. 응답 유실·재시작 후에는 실제 처리 결과를 확인한 다음 남은 작업을 이어간다.

### 화면 문구

| 상황 | 예시 |
|---|---|
| 대기 중 | “보고를 접수했어요. 잠시만 기다려 주세요.” |

### 검증과 완료 기준

- AI 초안 작업 중 다른 사용자의 채널 선택·제출이 AI 종료까지 기다리지 않는지 확인한다.
- 빠른 연속 클릭, 같은 보고 중복 제출, 수정과 제출의 경합, 서로 다른 보고 동시 처리를 검증한다.
- 전송 응답 유실, 문서 저장 중 일부 실패, 각 경계에서 재시작 후 복구를 검증한다.
- 접수 시간과 실제 저장 완료 시간을 따로 기록한다. 접수 안내만 빨라진 것을 전체 완료 시간 개선으로 표현하지 않는다.

**완료:** 사용자가 현재 상태를 알 수 있고, AI 대기로 제출이 막히는 현상이 줄며, 중복 없이 실패한 부분을 복구한다.
