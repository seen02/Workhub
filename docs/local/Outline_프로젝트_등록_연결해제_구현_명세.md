# Outline 프로젝트 등록·연결 해제 구현 명세

- 작성일: 2026-09-30
- 상태: 로컬 구현·적용 완료 / 실제 검증 범위는 [구현·검증 결과](Outline_프로젝트_관리_구현_검증_결과.md) 참조
- 작업 기준: `unified-work-assistant`의 현재 소스. `deployment/`는 별도 시점의 배포본이다.
- 사용자 요청: Workhub에서 하던 프로젝트 등록을 Outline 컬렉션 생성 흐름으로 옮기고, 연결 해제 화면까지 구현한다.
- 최초 작성 시에는 명세만 작성했으며, 후속 구현 요청에 따라 2026-09-30 코드와 로컬 실행 서비스를 변경했다. 기존 프로젝트·문서·업무의 보존을 최종 대조했다.

## 1. 목표와 구현 기본 결정

사용자는 Outline에서 컬렉션을 만들면서 업무 프로젝트로 등록하고, 이후 같은 컬렉션 메뉴에서 책임자 변경·연결 해제·재연결을 할 수 있어야 한다. Workhub는 등록된 프로젝트의 업무·통계·보고·검색을 계속 제공한다.

아래는 사용자가 세부 지정하지 않은 부분에 대한 **이 명세의 구현 기본값**이다. 구현자는 이를 기준으로 진행하고, 기술적으로 변경해야 하면 이유와 변경 내용을 이 문서에 기록한다.

|항목|구현 기본값|
|---|---|
|프로젝트 식별|Outline 컬렉션 ID와 Workhub 프로젝트 ID를 동일하게 유지|
|생성 진입점|Outline 기존 컬렉션 생성창에 `프로젝트로 연결 및 관리` 체크박스 추가. 기본은 해제|
|책임자 지정|컬렉션 생성 성공 후 Outline 안의 프로젝트 설정 모달에서 선택|
|기존 컬렉션|컬렉션 메뉴의 `프로젝트 관리 설정`에서 신규 연결 가능|
|연결 해제|같은 설정 모달에서 해제 확인창으로 이동. 기본은 문서 보존|
|기존 문서 삭제 옵션|기존 기능을 유지하되 고급 옵션으로 분리하고 명시적으로 선택해야 실행|
|등록·해제 권한|현재 Workhub 정책인 업무 관리자 + 해당 컬렉션 접근 권한 유지|
|책임자|활성 업무 관리자이며 해당 컬렉션에 접근 가능한 사람. 미지정 허용|
|Workhub 화면|신규 생성·연결·해제·책임자 변경 폼을 Outline 설정 진입 링크로 대체|
|저장 책임|문서와 컬렉션 권한은 Outline, 프로젝트 연결과 책임자는 Workhub|
|인증|Outline 로그인 사용자 → Outline 서버 → Workhub 내부 API. Workhub 선행 로그인 불필요|
|자동 연결|모든 컬렉션의 무조건 자동 등록, 이름 일치에 의한 자동 연결, 웹훅만으로 등록은 사용하지 않음|

기존 업무·보고·통계·검색 알고리즘을 재작성하지 않는다. 프로젝트 연결 상태 변경에 필요한 조회 차단·동기화·캐시 정리만 수정한다. 프로젝트 해제와 Outline 컬렉션 삭제는 별개 동작이다.

## 2. 현재 구현에서 확인한 사항

아래 경로는 이 명세가 있는 `unified-work-assistant` 기준이다.

|파일·함수|확인 내용 / 재사용 방향|
|---|---|
|`src/workhub/outline.py: register_project`|새 컬렉션 생성과 `existing_id`로 기존 컬렉션 연결 지원. 관리자 확인, 접근 확인, 책임자 기본 지정 포함|
|`src/workhub/outline.py: projects`|SQLite `kv.projects`가 연결 레지스트리. 현재 Outline 목록의 이름을 조회해 이름 변경 반영|
|`src/workhub/outline.py: project_managers`, `set_project_manager`|책임자 후보와 변경 기능 존재. 후보가 로컬 directory에 의존하는 부분 보완 필요|
|`src/workhub/outline.py: unlink_preview`, `unlink_project`|해제 대상 확인, 기본 문서 보존, 선택적 업무 목록 soft-delete, 업무 캐시 비활성화, 봇 문맥 제거 구현|
|`src/workhub/outline.py: task_parent`|업무 목록 문서 ID를 저장하고 재사용. 후속 변경으로 프로젝트 연결 완료 전에 자동 준비하며, 기존 최초 업무 생성 경로도 유지|
|`src/workhub/main.py`|프로젝트 생성·책임자·해제 API와 약 20초 간격의 업무/RAG 레지스트리 동기화 루프 존재|
|`src/workhub/auth.py`|Workhub 쿠키, 동일 Origin, CSRF 토큰 검사. Outline 프런트에서 기존 API를 직접 호출하는 방식은 그대로 사용할 수 없음|
|`src/workhub/permissions.py`|Outline 직접·그룹 접근 권한 확인. 업무 관리자 자격만으로 컬렉션 접근권을 주지 않음|
|`src/workhub/lifecycle.py`|Authentik 계정 조회, immutable UUID, `employee:<sub>` 계정 연결 기록, 활성 상태 검사 존재|
|`src/workhub/static/projects.js`|프로젝트 생성·책임자·연결 해제 모달 구현. 입력 항목과 동작을 이전할 때 참고|
|`src/workhub/search.py`|연결 프로젝트 목록을 문서 비서 RAG에 전달|
|`src/workhub/test_unlink.py`, `test_project_managers.py`, `test_permissions.py`|기존 핵심 회귀 테스트|
|`PROJECT-UNLINK-REPORT.md`, `ops/verify_unlink.mjs`|기존 해제 의미와 검증 시나리오|
|`.local/compose.json`|현재 설정의 Outline 이미지: `unified-work-assistant/outline:migration-baseline`, build 지정 없음|

설정 파일의 이미지 이름을 확인한 것이며, 실행 중 이미지의 버전·digest·소스 커밋까지 확인한 것은 아니다. Outline 공개 main 소스의 컬렉션 액션에서는 `openModal`과 `CollectionNew` 호출을 확인했다. 실제 설치 버전에서의 파일 위치와 API는 구현 0단계에서 확정한다.

## 3. 사용자 화면과 상태

### 3.1 컬렉션 생성

1. 기존 Outline 컬렉션 생성창의 이름·아이콘·색·공유/권한 설정은 유지한다.
2. 하단에 `프로젝트로 연결 및 관리` 체크박스와 `생성 후 책임자를 선택하면 Workhub의 업무·통계에 표시됩니다.` 설명을 추가한다.
3. 비관리자는 일반 컬렉션 생성 권한이 있으면 기존대로 생성한다. 프로젝트 등록 항목은 비활성화하고 관리자 전용임을 표시한다.
4. 업무 권한 확인 서버가 응답하지 않으면 등록 항목에 재시도를 제공한다. 일반 컬렉션 생성은 가능해야 한다.
5. 미선택이면 기존 생성 절차로 종료한다. 선택이면 **컬렉션 생성 성공 후** 해당 ID의 프로젝트 설정 모달을 연다.
6. 설정 모달에서 책임자를 선택하고 `프로젝트 등록`을 눌러야 최종 연결한다. 이 단계를 취소하면 컬렉션만 남는다. 연결 시 문서 작성 권한을 확인하고 최상위 `업무 목록` 문서를 준비한다. 기존 업무 목록은 재사용하며, 없으면 게시된 문서로 생성한다. 응답 유실 시 저장된 ID로 복구하고, 준비 완료 전에는 연결 성공으로 처리하지 않는다.
7. 생성 요청 응답 유실 시 신규 생성을 자동 반복하지 않는다. 서버에서 생성 결과를 조회할 수 있도록 요청 ID와 생성 결과를 연결하는 멱등성 처리를 구현한다. 설치 버전이 이를 지원하지 않으면 생성 작업 영수증을 추가한다.
8. 생성 완료 후 창이 닫히거나 새로고침되어도 컬렉션 메뉴에서 등록을 이어갈 수 있다. 연결되지 않은 컬렉션을 등록된 프로젝트로 표시하지 않는다.

권한 후보 조회는 실제 컬렉션이 생긴 후 수행한다. 따라서 생성 전 이름만 있는 단계에서 존재하지 않는 컬렉션 ID로 후보를 요청하지 않는다.

### 3.2 컬렉션 메뉴 → 프로젝트 관리 설정

컬렉션 메뉴에 `프로젝트 관리 설정`을 추가하고, 고정 ID를 이용하는 재진입 경로 `/workhub/projects/:collectionId`를 제공한다. URL은 Outline 안에서 모달을 여는 경로이며 직접 방문·새로고침도 지원한다. 접근 불가 컬렉션의 이름·책임자를 노출하지 않는다.

|상태|표시 및 동작|
|---|---|
|조회 중|로딩 표시, 변경 버튼 비활성화|
|미연결|현재 컬렉션명, `연결되지 않음`, 책임자 선택, `프로젝트 등록`|
|연결됨|`프로젝트 연결됨`, 현재 책임자, `책임자 저장`, `Workhub 열기`, `연결 해제…`|
|관리 권한 없음|접근 가능한 컬렉션의 연결 상태만 표시. 변경 버튼 비활성화|
|권한 확인 불가|`프로젝트 상태를 확인하지 못했습니다.`와 재시도. 미연결로 간주하지 않음|
|등록 처리 중|이중 제출 차단, 요청 ID 유지, `프로젝트 등록 중…`|
|등록 성공·동기화 대기|연결 완료 표시와 `업무·검색 정보를 반영 중입니다.` 보조 문구|
|일부 실패·결과 불명|상태 재확인 후 같은 요청 재시도. 신규 컬렉션을 다시 만들지 않음|

책임자 목록은 이름을 표시하고 동명이인은 이메일을 함께 표시한다. 저장에는 서버가 검증한 계정 식별자를 사용한다. 미연결 상태의 기본 선택은 등록자 본인으로 하되 자격이 없으면 미지정으로 둔다. 연결된 프로젝트는 저장된 책임자를 유지한다. 이미 연결된 컬렉션을 다시 등록해도 다른 사람이 지정한 책임자를 덮어쓰지 않는다.

### 3.3 연결 해제 확인창

기본 표시 예시:

```text
프로젝트 연결 해제
[컬렉션 이름]

Workhub의 프로젝트 목록·업무·진행 통계와 업무 비서의 프로젝트 선택에서 제외됩니다.
Outline 컬렉션, 문서, 첨부파일, 구성원 권한은 그대로 유지됩니다.
같은 컬렉션을 나중에 다시 연결할 수 있습니다.

고급 옵션 ▸
  □ 업무 목록과 그 아래 모든 문서를 휴지통으로 이동
    대상: [확인된 업무 목록 문서명]
    하위 문서도 함께 이동하며, 컬렉션과 업무 목록 밖의 문서는 유지됩니다.

[취소] [연결만 해제]
```

- 고급 옵션은 기본 접힘·미선택. 선택하면 실행 버튼을 `문서 휴지통 이동 후 연결 해제`로 변경한다.
- 문서 삭제 대상을 확인할 수 없거나 삭제 권한이 없으면 고급 옵션을 비활성화하고 이유를 표시한다. 연결만 해제는 해당 권한이 있으면 가능하다.
- 컬렉션 삭제 및 영구 삭제 옵션은 제공하지 않는다.
- 미리보기에는 확인된 업무 목록 ID·이름·URL, 프로젝트 연결 revision, 삭제 가능 여부를 포함한다. 문서 개수는 실제 계산한 경우에만 표시한다.
- 실행 시 현재 권한·연결 revision·업무 목록 ID와 위치를 다시 검증한다. 다른 문서로 바뀌었으면 409 후 미리보기를 다시 받는다.
- 성공 후 Outline은 현재 컬렉션 화면을 유지하고 미연결 상태로 갱신한다. 새 업무 목록 문서를 자동으로 만들지 않는다.
- 기본 해제는 모든 원본 문서·첨부파일·ACL을 보존한다. 고급 옵션만 명시한 하위 트리를 Outline 휴지통으로 이동한다.
- 취소·Esc·배경 클릭으로 닫을 때 실행하지 않는다. 서버 요청이 이미 진행 중이면 `처리 중` 상태를 유지하고 결과 확인 없이 취소됐다고 표시하지 않는다.

### 3.4 재연결 및 예외

- 미연결 컬렉션의 설정 모달에서 다시 등록한다. 동일한 컬렉션 ID를 사용한다.
- 기본 해제 후 재연결하면 기존 문서 ID, 업무 목록 ID, 보고 이력 원본을 재사용한다.
- 해제 전 책임자는 기록으로 보관하되 재연결 때 현재 자격을 검사하고 사용자가 선택한다.
- 고급 해제로 업무 목록을 휴지통에 보냈다면 재연결해도 복원하지 않는다. 재연결 시 기존 `task_parent` 정책에 따라 새 업무 목록을 만든다.
- 마지막 프로젝트를 해제해도 기본 컬렉션 자동 생성·자동 재연결이 발생하지 않는다.
- 컬렉션 이름 변경은 동일 ID의 표시명만 갱신한다. 같은 이름의 다른 컬렉션을 자동 연결하지 않는다.
- Outline에서 컬렉션을 삭제/보관하면 Workhub에서 접근·사용 대상에서 제외한다. Outline 자체의 복원은 연결 해제 기록을 지우지 않는다. 명시적으로 연결 해제했던 컬렉션은 복원만으로 재연결하지 않는다.
- 기존 등록 컬렉션 복제는 별개의 미연결 컬렉션으로 취급한다.

## 4. 시스템 구조와 인증

```text
Outline 프로젝트 모달
  → Outline의 인증된 /api/workhub.* 라우트
  → 고정된 내부 주소의 Workhub /internal/outline-projects/*
  → 계정·권한 확인 + 공통 프로젝트 서비스
  → 프로젝트 연결 저장 / 기존 Outline API / 동기화 작업
```

### 4.1 브라우저와 서버 경계

- Outline 프런트는 Outline의 기존 API 클라이언트·로그인·CSRF 규칙을 사용한다.
- Outline 서버 라우트에서 로그인 사용자의 ID와 team ID를 취득한다. 브라우저가 보낸 actor ID·이메일·관리자 여부는 신뢰하지 않는다.
- 브라우저에 Outline 서비스 API 키, Authentik 디렉터리 토큰, 서버 간 공유키를 내려주지 않는다.
- 기존 Workhub `auth.current`의 Origin/CSRF 검사를 완화하지 않는다. 기존 포털 API와 서버 간 전용 API를 구분한다.
- Workhub iframe은 사용하지 않는다. 현재 Workhub는 `X-Frame-Options: DENY`, `frame-ancestors 'none'`을 설정한다.

### 4.2 서버 간 인증 계약

전용 키 `OUTLINE_WORKHUB_BRIDGE_SECRET`와 고정 내부 목적지 `WORKHUB_INTERNAL_URL`을 사용한다. 기존 AI용 `AGENT_TOKEN`을 재사용하지 않는다.

요청은 HMAC-SHA256으로 `method + path + timestamp + nonce + SHA256(raw_body)`를 서명한다. 필드 구분과 인코딩은 공통 테스트 벡터로 고정한다. Workhub는 상수 시간 서명 비교, ±60초 timestamp, nonce 중복 사용 방지, 허용된 Outline team ID를 확인한다. nonce는 영속 저장하고 허용 시간보다 길게 보존한다. HTTP 재시도는 새 nonce와 같은 업무 request ID를 사용한다.

내부 API는 공개 프록시 경로에서 차단하고 서비스 네트워크로 제한한다. 서버가 사용자 입력 URL로 요청하지 않도록 목적지를 고정한다. 내부 네트워크를 벗어나면 TLS를 사용한다.

### 4.3 사용자 식별과 현재 권한

1. 서명된 요청의 Outline 사용자 ID·team ID를 Outline 서버가 보증한다.
2. Workhub는 Outline 사용자 상태와 저장된 `employee:<sub>.outline_id` 연결을 확인한다. immutable Authentik UUID에 연결된 계정이어야 한다.
3. Authentik 디렉터리 API로 해당 UUID의 현재 활성 상태, 업무 사용자 그룹, 업무 관리자 그룹을 조회한다. 오래된 `directory.people().admin` 값만으로 변경을 허용하지 않는다.
4. 이메일이 변경·중복되었거나 계정 연결이 검토 상태면 변경을 거부하고 계정 동기화 안내를 표시한다. 같은 이메일의 새 계정을 이전 UUID로 자동 연결하지 않는다.
5. Workhub에 로그인한 적이 없어도 계정 연결이 동기화되어 있으면 사용 가능해야 한다. `auth.for_subject()`의 저장된 포털 토큰을 필수로 요구하지 않는다.
6. 연결 기록이 없으면 기존 계정 동기화 절차로 검증된 매핑을 만든 뒤 재시도한다. 임의 이메일 매칭으로 관리자 권한을 만들지 않는다.
7. 신규 bridge에서는 디렉터리 설정이 없거나 조회에 실패하면 변경을 차단한다. 현재 일부 함수의 `enabled() == False` 우회 동작을 그대로 인증 근거로 사용하지 않는다.

책임자 후보도 활성 Authentik 관리자와 Outline 접근 가능 구성원의 교집합으로 구한다. UI 후보 조회와 실제 저장 양쪽에서 검증한다.

### 4.4 권한 표

|동작|필요 조건|
|---|---|
|일반 컬렉션 생성|Outline 자체 생성 정책|
|프로젝트 상태 조회|활성 업무 사용자 + 해당 컬렉션 읽기 권한|
|연결·책임자 변경·기본 해제|활성 업무 관리자 + 해당 컬렉션 읽기 권한|
|업무 목록 휴지통 이동 포함 해제|위 조건 + Outline의 대상 문서 삭제 정책상 실행 가능|
|책임자로 지정|활성 업무 관리자 + 해당 컬렉션 읽기 권한|

새 연동이 컬렉션 구성원·기본 공개 범위·그룹 권한을 자동 확대하지 않는다. 서비스 계정이 새 private 컬렉션을 조회할 수 있는지도 0단계에서 검증한다. 접근할 수 없는 경우 공개 전환으로 해결하지 말고, 명시적인 서비스 계정 운영 권한을 구성하거나 등록 불가 사유를 표시한다.

## 5. API 계약

아래 이름은 **신규 구현 계약**이다. 현재 존재하는 엔드포인트로 오해하지 않는다. Outline 쪽 응답 외피는 설치 버전의 표준 API 형식을 따른다.

|Outline POST 라우트|내부 POST 라우트|역할|
|---|---|---|
|`/api/workhub.capabilities`|`/internal/outline-projects/capabilities`|사용자 등록 자격 및 연동 가능 여부|
|`/api/workhub.projectInfo`|`/internal/outline-projects/info`|연결 상태, 책임자, revision, 가능한 동작|
|`/api/workhub.projectManagers`|`/internal/outline-projects/managers`|미연결 컬렉션도 포함한 책임자 후보 조회|
|`/api/workhub.projectLink`|`/internal/outline-projects/link`|기존 컬렉션 ID로 등록·재연결|
|`/api/workhub.projectManagerUpdate`|`/internal/outline-projects/manager`|책임자 변경|
|`/api/workhub.projectUnlinkPreview`|`/internal/outline-projects/unlink-preview`|해제 영향·대상·권한 조회|
|`/api/workhub.projectUnlink`|`/internal/outline-projects/unlink`|기본 또는 고급 연결 해제|
|`/api/workhub.projectOperation`|`/internal/outline-projects/operation`|응답 유실 시 요청 처리 결과 조회|

Outline 요청의 기본 필드는 `collectionId`이다. 변경 요청은 `requestId`와 `expectedRevision`을 추가한다. 내부 body에는 서버가 확정한 `actor: {outlineUserId, outlineTeamId}`를 추가한다. 신규 모델은 알 수 없는 필드를 거부한다.

등록 입력 예시:

```json
{
  "collectionId": "<outline-collection-uuid>",
  "requestId": "<uuid>",
  "expectedRevision": 0,
  "managerSubject": "<authentik-uuid-or-null>"
}
```

해제 입력 예시:

```json
{
  "collectionId": "<outline-collection-uuid>",
  "requestId": "<uuid>",
  "expectedRevision": 3,
  "deleteTaskList": false,
  "expectedParentId": null
}
```

- `deleteTaskList=true`일 때 확인된 `expectedParentId`가 필수다. `false`일 때는 null이어야 한다.
- info는 `linked`, `revision`, `project`, `permissions`, `syncStatus`를 반환한다. 미연결이어도 해제 이력이 있으면 revision은 0으로 돌아가지 않는다.
- 변경 결과는 `requestId`, `operationStatus`, `linked`, `revision`, `syncStatus`를 반환한다.
- `operationStatus`: `completed`, `pending`, `failed`. 결과 불명 상태는 클라이언트가 operation 조회로 확인하며, 실패로 단정해 새 요청을 만들지 않는다.
- `syncStatus`: `pending`, `synced`, `error`. 연결 저장과 업무·검색 동기화 결과를 분리한다.
- 오류: 401 인증 실패, 403 자격/권한 부족, 404 대상 없음, 409 revision/요청 충돌, 422 입력 오류, 503 연결·권한 확인 불가. Outline 표준 오류 외피에 기계 판별 code를 포함한다.
- operation 조회도 현재 사용자 자격과 대상 접근권을 다시 검사한다. request ID만으로 타인의 결과·프로젝트 정보를 열람할 수 없어야 한다.

기존 `/api/projects` 계열은 전환 기간 공통 서비스에 위임한다. Outline 전환 활성화 후 포털 UI의 변경 폼은 제거하고, 구형 변경 요청에는 409 `project_management_moved`와 Outline 설정 URL을 반환한다. 읽기 API는 유지한다. 기능 플래그를 끄면 기존 화면·변경 경로로 복구 가능해야 한다.

## 6. 데이터·멱등성·동시성

### 6.1 저장 원칙

- `kv.projects`는 연결된 프로젝트 레지스트리로 유지한다. 프로젝트 이름은 Outline 현재 이름을 사용한다.
- 연결·해제·책임자 변경을 하나의 공통 서비스로 모은다. 기존 봇·업무 코드를 새 레지스트리로 전면 전환하지 않는다.
- 신규 `project_link_state` 테이블에 `collection_id` 기본키, `revision`, `linked`, `last_manager_subject`, `last_manager_email`, `updated_at`을 저장한다. 해제 후에도 행을 보존한다.
- 신규 `project_operations`에 `request_id` 기본키, `actor_subject`, `collection_id`, `action`, `payload_hash`, `expected_revision`, `status`, `result`, `created_at`, `updated_at`을 저장한다. 영수증만으로 권한을 부여하지 않는다.
- 신규 `project_sync_jobs`에 컬렉션별 필요한 최신 revision·재시도 시점·시도 횟수·최근 오류를 저장한다. 레지스트리 변경과 같은 DB 트랜잭션에서 작업을 기록한다.
- 신규 `bridge_nonces`는 서명 재사용 방지용이다. 업무 멱등성 영수증과 구분하고 만료 후 정리한다.
- 기존 연결 프로젝트는 revision 1로 이관하고 기존 책임자·ID를 보존한다. 책임자 UUID를 확정하지 못하면 기존 이메일을 보존하되 다음 변경 때 검증한다. 미연결 신규 컬렉션은 revision 0으로 조회한다.

### 6.2 변경 트랜잭션

1. 현재 사용자·대상·책임자/삭제 권한을 검증한다.
2. 같은 request ID의 영수증을 확인한다. actor/action/payload가 다르면 409, 완료된 동일 요청이면 기존 결과를 반환한다.
3. DB에서 expected revision을 비교한다. 다른 변경이 선행했으면 409로 새 상태를 다시 보여준다.
4. 연결 상태, `kv.projects`, 해당 작업 결과, 동기화 작업을 일관되게 기록한다. 해제 시 업무 캐시 비활성화와 봇 문맥 정리도 함께 처리한다.
5. 서버 재시작과 다중 요청을 견딜 수 있도록 SQLite 트랜잭션/조건부 갱신을 사용한다. 프로세스의 `threading.RLock`만을 동시성 보장으로 삼지 않는다.
6. 외부 네트워크 호출 중 DB 쓰기 트랜잭션을 장시간 유지하지 않는다. 고급 해제는 영속 pending 작업과 revision 예약으로 다른 프로젝트 변경을 차단하고, 원격 처리 후 최종 확정한다.

같은 컬렉션 등록을 서로 다른 request ID로 동시에 보내도 활성 연결은 하나여야 한다. 오래된 등록 요청은 해제 후 재연결을 만들지 않아야 하고, 오래된 해제 요청은 재연결된 프로젝트를 다시 끊지 않아야 한다. 완료 영수증의 revision이 현재보다 오래되면 과거 결과임을 구별해 반환하고 UI는 최신 info를 조회한다.

### 6.3 원격 작업의 일부 성공

|상황|처리|
|---|---|
|컬렉션 생성 성공, 프로젝트 등록 미실행/실패|컬렉션 보존. 해당 ID의 설정에서 등록 재개|
|등록 저장 성공, 응답 유실|같은 request ID로 결과 조회/재전송. 책임자·연결 중복 생성 금지|
|등록 성공, 업무/RAG 동기화 실패|연결은 성공 유지, 동기화 상태만 오류/재시도 대기로 표시|
|기본 해제 응답 유실|영수증과 최신 상태로 완료 확인. 새 해제 작업을 임의 생성하지 않음|
|업무 목록 삭제 실패|프로젝트 연결 유지. 실패 이유 표시|
|삭제 성공, 응답 유실/Workhub 재시작|저장된 의도와 실제 휴지통 상태를 확인해 해제 확정. 같은 문서를 다시 생성하거나 다른 문서를 삭제하지 않음|
|삭제 결과 확인 불가|pending 유지, 조회/재시도 제공. 성공 또는 미실행으로 단정하지 않음|
|작업 중 권한 철회|추가 원격 변경을 차단. 일부 수행 상태는 영수증에 기록하고 자격 있는 관리자가 재검증 후 복구|

## 7. 연결 해제의 전체 반영 범위

1. Workhub 프로젝트 선택·업무 보드·전체/개별 통계에서 제외한다.
2. 해당 프로젝트 업무 캐시를 비활성화하고 통계 관측 이력은 삭제하지 않는다. 조회 시 현재 등록 범위를 적용한다.
3. 봇 프로젝트 선택·현재 선택 문맥·이전 버튼·보고 초안 확정 시 연결 상태를 다시 검사한다. 이미 열린 화면으로 해제된 프로젝트에 보고할 수 없어야 한다.
4. 연결 해제와 보고 확정이 동시에 일어날 때 서버의 처리 순서를 정하고, 해제 완료 이후 새 문서 쓰기가 시작되지 않도록 공통 실행 경계에서 재검증한다. 이미 완료된 보고를 자동 되돌리지 않는다.
5. Workhub 프로젝트 기반 RAG의 대상 목록에서 제외한다. 색인 정리는 지연될 수 있어도 응답 생성·인용 반환 전에 현재 연결과 ACL을 확인해 해제된 프로젝트 자료를 반환하지 않는다.
6. 일반 Outline 직접 검색·문서 열기는 본래 ACL대로 가능하다. 프로젝트 연결 해제를 컬렉션 접근권 회수로 해석하지 않는다. 일반 문서 비서가 별도로 허용한 검색 범위까지 임의로 제거하지 않는다.
7. Workhub의 열린 화면은 기존 새로고침/폴링 주기에 상태를 갱신하고, 포커스 복귀 시 목록을 재조회한다. 서버 쓰기 차단은 폴링을 기다리지 않는다.
8. 마지막 프로젝트가 없어졌을 때 `Outline에서 프로젝트 등록` 안내를 표시한다. 무관한 기존 사용자 데이터를 초기화하지 않는다.

정상 환경에서 연결 목록 갱신은 작업 직후, 기존 탭의 자동 반영은 다음 폴링 주기, 백그라운드 동기화 착수는 30초 이내를 목표로 한다. 전체 색인 완료 시간은 문서량에 따라 다르므로 고정 완료 시간을 약속하지 않는다.

|Workhub 기존 코드|`main.py`, `outline.py`, `store.py`, `permissions.py`, `lifecycle.py`, `search.py` 및 필요한 보고/봇 실행 경계|
|Workhub UI|`static/projects.js`, `static/index.html`: 관리 폼을 Outline 진입 링크로 전환하고 빈 상태 처리|
|설정|기능 플래그, 내부 URL, 허용 team ID, 별도 secret, 커스텀 Outline 이미지 태그/digest. 비밀값은 비공개 설정에만 저장|
|프록시|공개 `/internal/outline-projects/*` 접근 차단. CORS 전면 허용 또는 CSP 완화로 우회하지 않음|
|테스트·운영 문서|bridge/상태 전이/통합 UI 테스트, 검증 보고서, 운영·업데이트·롤백 안내|

Outline 변경은 런타임 번들 문자열 치환이나 컨테이너 안의 임시 수정을 납품 방식으로 사용하지 않는다. 고정 upstream 소스 + 관리되는 패치 + 재현 가능한 이미지 빌드로 관리한다. 저장소 라이선스·고지·기존 수정사항을 유지한다. 최신 main으로 무조건 업그레이드하지 않는다.

## 11. 운영·롤백

- 기능 플래그 `OUTLINE_PROJECT_MANAGEMENT_ENABLED`를 Outline UI/서버와 Workhub 전환 정책에 일관되게 적용한다. 환경별 적용값을 배포 문서에 기록한다.
- 먼저 추가형 DB 마이그레이션과 공통 서비스를 배포하고, bridge와 새 Outline 이미지를 검증한 후 UI 전환을 활성화한다.
- 변경 작업의 actor UUID, 컬렉션 ID, action, request ID, 이전/새 revision, 결과, 시각을 기록한다. API 키·세션·서명키·문서 본문은 작업 로그에 넣지 않는다.
- 이전 이미지 digest와 설정을 보존한다. 롤백은 기능 플래그/이미지 전환을 우선하고, 새 정상 연결 데이터를 지우기 위해 과거 DB를 무조건 복원하지 않는다.
- pending 삭제 작업이 있으면 UI를 되돌리기 전에 처리 결과를 확인한다. 이전 코드가 진행 중 작업을 무시하고 변경하지 않도록 유지보수 차단 또는 호환 공통 서비스를 유지한다.
- Outline 업데이트마다 고정 버전을 새로 정하고 패치 적용, 인증, 생성, 기본 해제, 선택 삭제, 재연결을 재검증한다.
- 실제 인증 정보는 `.local` 등 비공개 설정으로 관리하고 명세·패치·Git·배포 안내 예시에 넣지 않는다.

## 12. 최종 완료 기준

아래 항목을 모두 만족해야 완료로 보고한다.

- Outline에서 컬렉션 생성과 프로젝트 등록을 연속 수행할 수 있다.
- 기존 컬렉션 연결, 책임자 변경, 문서 보존 해제, 고급 해제, 재연결 화면이 동작한다.
- Workhub의 프로젝트 관리 진입점이 Outline 설정으로 연결된다.
- 사용자 자격·컬렉션 ACL·삭제 정책이 서버에서 검증된다.
- 일부 성공, 응답 유실, 재시작, 과거 요청 재전송이 중복 등록·재해제·문서 오삭제를 만들지 않는다.
- 업무·통계·봇·프로젝트 검색이 연결 상태를 따르며 기존 정상 프로젝트에 회귀가 없다.
- 실제 설치 버전에 맞춘 빌드·패치·검증 기록·롤백 안내를 남긴다.
