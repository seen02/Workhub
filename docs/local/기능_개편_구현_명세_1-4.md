# Outline–Rocket.Chat 통합 업무 관리 시스템: 기능 개편 구현 명세

작성일: 2026-09-29  
상태: 1번 보고 개편 구현 및 로컬 검증 완료. 2026-09-30 업무 인식 오류 수정 적용. 2번 검색 강화는 로컬 구현·핵심 실행 검증을 완료했으며 전체 타입 검사·운영 부하 검증은 남아 있다. [검색 구현·검증 결과](검색_기능_강화_구현_검증_결과.md), 업무 인식 복구 기록 (`reports/report-task-scope-repair-20260930.md`; 로컬 자료), 통합 검증 기록 (`reports/report-combined-validation-20260929.md`; 로컬 자료)을 참고한다.  
대상: 이 저장소를 읽고 실제 구현·검증을 진행할 개발자 및 AI 에이전트.

## 목적과 진행 순서

직원은 여러 업무의 진행 상황을 채팅으로 한 번에 보고하고, 확인한 내용을 Outline 업무에 반영한다. 아직 등록되지 않은 업무는 같은 흐름에서 새 업무 문서로 추가한다. 보고 양식은 업무 문서명과 각 업무의 완료 기준을 중심으로 구성한다. 필요한 지식은 질문으로 찾는다. Workhub는 프로젝트 연결과 업무 현황 관리를 지원한다. 여유가 생기면 채팅에서 해결한 내용을 지식 문서로 남기는 기능까지 추가한다.

| 순서 | 작업 | 사용자가 확인할 결과 |
|---|---|---|
| 1 | Rocket.Chat 보고 기능 개편 | 자유롭게 입력 → RAG 기반 업무·완료 기준 탐색 → 통합 보고 초안 → 보고하기 / 기존 업무 수정·새 업무 추가 |
| 2 | Outline 검색 기능 강화 | 기존 Outline 검색 화면에 RAG 답변 결합, Rocket.Chat 멘션으로 문서 링크 검색, 검색 대상 자동 등록·갱신 |
| 3 | Workhub 프로젝트 등록 간편화 | 기존 Outline 컬렉션을 쉽게 찾아 프로젝트로 연결 |
| 4 | Rocket.Chat 대화 기반 문서 생성 | 선택한 대화를 정리 → 검토 → Outline 문서로 저장. 시간 여유가 있을 때 진행 |

- 반드시 **1 → 2 → 3 → 4** 순서로 진행한다. 1·2번은 기존 프로젝트 등록 기능을 이용하며, 3번 개편을 선행 조건으로 만들지 않는다.
- 1번에서 기존 검색 기반을 재사용해 보고 대상 탐색과 신규 업무의 즉시 조회를 구현한다. 2번에서 검색 대상 자동 관리·색인 복구·관리자 설정을 완성하고, 3번에서 프로젝트 연결 화면과 연결 상태 안내를 간소화한다. 1번의 RAG 탐색을 2번 이후로 미루지 않는다.
- 사용자가 “1번 구현해줘”라고 하면 1번 범위를 구현·검증한다. 다른 번호까지 임의로 확장하지 않는다.
- 각 단계 종료 후 이 문서 마지막의 진행 기록을 갱신한다. 구현 내용, 실제 검증 범위, 남은 제한을 구분한다.
- 이번 명세 작성 자체는 소스 코드 변경, 운영 데이터 변경, 배포를 의미하지 않는다.

## 현재 구현과 반드시 유지할 부분

아래는 개편 전 로컬 소스와 당시 Outline 업무 문서 형식을 확인한 내용이다. 개편 후 결과는 마지막 진행 기록을 참고한다. 로컬 구현과 현재 실행 중인 서비스·배포본은 다를 수 있으므로, 단계 시작 시 다시 확인한다.

| 영역 | 확인한 현재 상태 | 이번 작업과의 관계 |
|---|---|---|
| 보고 | Workhub 보고 API는 선택한 업무 하나를 중심으로 초안을 생성한다. Rocket.Chat 봇의 구독 경로는 현재 DM 중심이다. | 기존 통합 업무 비서 개인 대화방 진입을 유지하고, 여러 업무를 묶는 보고 모델과 선택한 채널·토론방으로의 전송을 추가해야 한다. |
| Outline 반영 | 변경 제안 생성·확정·충돌 확인·재시도 복구 경로가 있다. | 문서별 반영에 재사용한다. 여러 문서를 한 번에 원자적으로 저장할 수 있다고 가정하지 않는다. |
| 직접 업무 작성 | 연결된 컬렉션의 최상위 `업무 목록` 바로 아래에 게시한 템플릿 문서를 업무로 인식한다. 사람이 읽는 담당자·체크박스 형식을 지원한다. | 새 보고 기능도 이 형식을 보존해야 한다. 기존 코드 포함 업무 문서도 계속 지원한다. |
| 검색 | 선택 프로젝트 검색과 문서 에이전트의 근거 검색 경로가 있다. 검색 대상은 등록·설정 범위의 영향을 받는다. | 모든 Outline 문서를 이미 검색한다고 설명하면 안 된다. 검색 범위와 내용 정확성을 함께 개선한다. |
| 프로젝트 연결 | 관리자용 기존 컬렉션 연결·신규 컬렉션 생성 API와 화면이 있다. | 처음부터 다시 만드는 작업이 아니라 기존 흐름의 간소화다. |
| 문서 생성 | 문서 에이전트에 초안·저장·수정 흐름이 있다. | Rocket.Chat 대화 선택·수집·사용자 권한 전달을 연결하는 작업은 별도로 필요하다. |

공통 구현 원칙:

1. Outline 문서를 업무 원본으로 유지한다. Workhub에 별도 업무 원본을 만들어 양쪽을 수동 관리하게 하지 않는다.
2. 기존 사람용 템플릿, 자유 메모, 결과물 링크, 진행 기록을 보존한다. 사람용 문서에 내부 식별 코드를 노출하지 않는다.
3. 표시 이름만으로 사용자를 판단하지 않는다. 기존 Authentik 계정 연결과 현재 권한 검사를 이용한다.
4. AI는 보고 내용을 해석하고 초안을 만든다. 접근 권한, 변경 가능 항목, 실제 저장은 서버가 판단한다.
5. 초안 생성만으로 채널 전송·업무 수정·문서 게시를 실행하지 않는다. 각 화면에서 사용자가 요청한 동작만 실행한다.
6. 데이터베이스 변경은 기존 초안·보고 이력을 보존하는 추가형 마이그레이션으로 한다. 서비스 재시작 후에도 처리 상태가 남아야 한다.
7. 단계 시작 시 현재 변경 사항과 실행 중인 소스 버전을 확인한다. 다른 작업의 변경을 되돌리거나 기존 데이터를 초기화하지 않는다.
8. 외부 API·버튼·권한 동작은 실제 설치 버전에서 확인한다. 아래에 제안한 새 데이터 구조·API 이름은 기존 구현이 있다는 뜻이 아니다.

## 1. Rocket.Chat 보고 기능 개편

### 1.1 목표와 범위

**업무마다 들어가 체크리스트를 바꾸는 흐름을, 여러 업무의 보고를 한 번에 작성하는 흐름으로 바꾼다.** 기존 보고 템플릿의 보기 좋은 형식은 유지한다.

필수 범위:

- 보고 입력·초안 검토·수정·반영은 기존 **통합 업무 비서 개인 대화방(DM)**에서 진행한다. 채널 멘션으로 봇을 호출하는 흐름은 보고 기능의 진입 방식으로 구현하지 않는다.
- 한 입력에 여러 업무와 여러 프로젝트를 포함할 수 있다.
- 프로젝트·업무·완료 기준의 정확한 이름을 입력하지 않아도 RAG 의미 검색과 이름·키워드 검색으로 실제 대상을 찾는다. 약칭·일상 표현·일부 오타를 허용하고 모호한 부분만 질문한다.
- `[업무목록]`에는 업무 문서명을, 각 업무 아래 `1. 2. 3.`에는 완료 기준과 상태를 표시한 통합 보고 초안을 만든다. 프로젝트명을 업무 문서명 대신 넣지 않는다.
- 없는 업무는 프로젝트와 생성 내용을 초안에서 확인한 뒤, 같은 보고 흐름에서 새 업무 문서로 추가할 수 있다.
- 사용자가 초안을 고치고 목적지를 확인할 수 있다.
- `보고 및 반영`을 누르면 채널·토론방 선택 화면이 열린다. 매번 목적지를 선택하며 `뒤로 가기`는 실행 없이 초안으로 돌아간다.
- 채널 버튼을 누르면 보고 게시와 Outline 기존 업무 변경·새 업무 생성을 함께 처리한다. 별도의 보고 전용·반영 전용 버튼은 제공하지 않는다.
- 두 서버의 결과를 내부에서는 따로 기록하되 화면에는 간단한 완료 안내를 보여준다. 일부 실패를 전체 성공으로 표시하지 않는다.
- 직원이 이 흐름을 사용하기 위해 매번 Workhub 웹 화면으로 이동할 필요가 없어야 한다.

보고에서 언급한 미등록 업무의 생성은 이번 범위에 포함한다. 사용자가 요청하지 않은 업무를 AI가 임의로 발굴·생성하는 기능, 개인 성과 평가, 보고 내용만으로 완료 품질을 판정하는 기능은 포함하지 않는다.

### 1.2 목표 사용 흐름

1. 직원이 기존 **통합 업무 비서 개인 대화방**을 열고 보고 내용을 입력한다. 예: `팀 협업 시연 프로젝트의 로그인 업무는 화면 구현을 완료했고 오류 메시지 검수는 진행 중이야. 배포 업무는 Docker 파일 작성을 완료했고 설치 검증은 예정이야.` 멘션은 필요 없다. 기존 보고 메뉴를 통해 보고 모드에 들어갈 수도 있으며, 특정 업무를 하나씩 선택해야만 입력할 수 있게 제한하지 않는다.
2. 봇이 같은 개인 대화방에서 통합 초안과 `보고 및 반영 / 수정 / 더보기` 버튼을 제공한다. 채널은 보고 및 반영을 누른 다음 매번 선택한다.
3. RAG와 이름·키워드 검색으로 프로젝트·업무·완료 기준을 찾고 최신 원문으로 확인한다. 명확하면 자동 연결하며 이름이 겹치거나 불명확한 부분만 후보를 제시한다. 실제로 없는 업무는 `새 업무로 추가 예정`으로 표시한다. 이미 명확한 항목을 다시 선택시키지 않는다.
4. 직원이 같은 개인 대화방에서 보고 초안·보고할 곳·반영 내역을 확인·수정한다. 기존 업무 변경과 새 업무 생성이 구분되고, 신규 업무의 저장 프로젝트·문서명·담당자·완료 기준·초기 상태가 보인다.
5. 개인 대화방의 `보고 및 반영`을 누르면 채널/토론방 선택 버튼과 `뒤로 가기`가 나온다. 뒤로 가기는 실행 없이 초안으로 돌아간다.
6. 채널 버튼을 누르면 사전 검증 → 보고 게시 확인 → 기존 항목 갱신·새 업무 생성 순서로 실행한다. 별도의 반영 클릭을 요구하지 않는다. 결과 링크는 개인 대화방에 보여준다.
7. 개인 대화방에는 `보고 전송 완료 / 기존 업무 1건 수정·새 업무 1건 추가 완료`처럼 두 결과와 처리 종류가 함께 남는다. 보고 채널에는 최종 보고문을 전송한다.

토론방은 독립된 방 ID, 스레드는 부모 메시지 ID를 갖는 별도 개념으로 취급한다. 채널·토론방은 **보고를 받는 목적지**로 검증하고 스레드 목적지 지원 여부는 설치 버전을 확인해 명시한다. 1번 보고 기능을 위해 채널의 일반 대화나 멘션을 구독·처리하는 기능을 추가하지 않는다. 4번의 선택한 대화 수집은 별도 범위다.

보고 목적지 선택 규칙:

- 개인 대화방에서 이름으로 검색·선택할 수 있게 한다. 사용자가 접근하고 보고를 게시할 수 있으며 봇도 전송할 수 있는 채널·토론방만 목적지로 허용한다. 봇 서비스 계정의 권한만으로 사용자에게 없는 게시 권한을 대신 부여하지 않는다.
- 목적지는 매번 채널 버튼으로 선택한다. 이전 선택으로 자동 실행하지 않는다. 실행 후에는 보고 초안별 목적지를 고정한다.
- 채널 선택 전에는 게시·반영이 모두 실행되지 않는다. `보고할 곳 변경` 메뉴는 제공하지 않는다.
- 전송 직전 사용자 접근·게시 권한과 봇 전송 가능 여부를 재확인한다. 목적지가 삭제되거나 권한이 바뀌면 개인 대화방에서 재선택을 안내하고 초안을 보존한다.
- 초안·수정 대화·실패 안내는 개인 대화방에 유지한다. DM에서 보고 내용을 입력한 사실만으로 채널에 전송하지 않는다.

#### 보고 양식: 필수 형식

`업무목록`은 해당 프로젝트의 `업무 목록` 아래에 있는 **개별 업무 문서의 제목 목록**이다. 프로젝트명이나 부모 문서 제목인 `업무 목록` 자체를 나열하는 것이 아니다. 새 업무는 생성 예정 문서명을 쓴다.

입력 예: `팀 협업 시연 프로젝트의 로그인 업무는 화면 구현을 완료했고 오류 메시지 검수는 진행 중이야. 배포 업무는 Docker 파일 작성을 완료했고 설치 검증은 예정이야.`

채널에 전송할 보고 본문:

```markdown
**[업무목록]**

- 로그인 업무
- 배포 업무

**[9월 29일 화요일 : 13시 00분]**

**로그인 업무**

1. 화면 구현(✅ 완료)
2. 오류 메시지 검수(⏳ 진행 중)

**배포 업무**

1. Docker 파일 작성(✅ 완료)
2. 설치 검증(🕒 예정)
```

표시 규칙:

- 상단에는 업무 문서명을 중복 없이 나열한다. 본문에서는 같은 순서로 각 업무명을 굵게 표시한다.
- `1. 2. 3.`은 해당 업무의 **완료 기준**이다. 프로젝트나 업무를 번호 목록에 넣지 않는다. 업무가 바뀌면 번호를 1부터 다시 시작한다.
- 상태는 `✅ 완료`, `⏳ 진행 중`, `🕒 예정`으로 구분한다. 입력이 `진행 중`이면 `예정`으로 바꾸지 않는다. 기존 다른 상태를 표시할 때도 의미를 바꾸지 않는다.
- 원칙적으로 이번 보고에서 언급한 기준을 입력 순서로 표시한다. 언급하지 않은 기준을 임의로 예정 처리하거나 보고문에 추가하지 않는다. 기존 업무의 나머지 기준은 Outline에서 그대로 보존한다.
- 기존 업무에서 `기준 1`, `기준 2`라고 말하면 해당 원문의 실제 완료 기준명을 찾아 표시한다. 새 업무처럼 참조할 기준이 없으면 구체적인 기준명을 확인하고, 의미 없는 번호를 실제 기준명으로 대신 저장하지 않는다.
- 여러 프로젝트의 업무도 동일한 양식으로 묶는다. 같은 업무명이 겹칠 때만 업무명 옆에 `(프로젝트명)`을 붙여 구분한다. 내부에는 항상 프로젝트 ID·문서 ID 연결을 유지한다.
- 날짜·요일·시간은 고정된 보고 시각에서 계산한다. 내부에는 연도·시간대까지 보존하되 본문은 위 양식을 따른다.
- 버튼·처리 상태·신규 생성 안내는 초안 검토 화면의 별도 영역에 표시한다. 채널에 전송되는 보고 본문에 조작 안내를 섞지 않는다.
- 위 예시는 표시 결과의 기준이다. 실제 Rocket.Chat 설치 버전에 맞춰 굵게·줄바꿈·번호 목록을 렌더링하고 실제 화면에서 확인한다.

개인 대화방의 초안 검토 영역에 표시할 별도 반영 안내 예시:

```text
새로 만들 내 업무: 배포 업무
[보고 및 반영] [수정] [더보기]

보고 및 반영 클릭 후:
어디에 보고할까요?
채널을 누르면 보고를 보내고 업무에도 반영해요.
[demo] [다른 채널] [뒤로 가기]
```

예시 프로젝트·계정·항목은 테스트용이다. 실제 데이터에 임의로 만들거나 적용하지 않는다.

### 1.3 해석과 반영 규칙

- 보고 원문과 사용자가 확정한 보고문을 모두 보존한다. 원문에 없는 날짜·진행률·완료 사항을 추가하지 않는다.
- 보고 시각은 명시한 값을 우선하고, 없으면 초안 생성 시각을 한국 시간으로 한 번 고정한다. 클릭할 때마다 보고 시각을 바꾸지 않는다.
- 기존 프로젝트·업무·완료 기준은 서버가 조회한 실제 ID에 연결한다. 신규 업무는 서버가 생성 요청 ID를 발급하고 생성 결과의 실제 문서 ID에 연결한다. AI가 만든 ID를 그대로 저장하지 않는다.
- 같은 업무의 여러 항목은 하나의 문서 변경 제안으로 합친다. 같은 문서에 서로 충돌하는 제안을 연속 생성하지 않는다.
- `로그인은 완료`가 업무 전체인지 일부 완료 기준인지 불명확하면 확인한다. 일부분 완료를 전체 완료로 확대하지 않는다.
- 기존 체크리스트 업무의 진행률은 기존 계산 규칙을 따른다. 사용자가 보고한 `80%`를 체크리스트 완료율과 동일한 값으로 덮어쓰지 않는다. 필요한 경우 보고 원문에 남긴다.
- 항목 없는 기존 업무는 현재 지원하는 상태·진행률 변경 경로를 유지한다. 적용 가능한 필드를 초안에서 보여준다.
- 매칭하지 못한 내용도 보고문에서 삭제하지 않는다. 확인된 미등록 업무는 `새 업무로 추가 예정`, 후보가 여러 개이거나 조회에 실패한 항목은 `연결 확인 필요`로 구분한다. 보고만 하거나, 기존 업무에 연결하거나, 새 업무를 추가할 수 있다.
- 미해결 항목이 있으면 기본적으로 반영을 보류한다. 사용자가 특정 항목을 명시적으로 제외한 경우에만 나머지를 반영하며 제외 내역을 남긴다.
- 권한 없는 변경은 실행하지 않는다. 보고문 작성 권한과 Outline 수정 권한을 동일하다고 가정하지 않는다.
- 반영 시 보고 이력에는 해당 업무에 관련된 내용과 전체 보고 ID를 남긴다. 다른 프로젝트의 전체 보고를 모든 업무 문서에 복제하지 않는다.
- 보고 채널의 공개 범위를 확인한다. AI가 검색한 비공개 문서 내용을 권한이 더 넓은 채널 보고문에 자동 삽입하지 않는다. 초안에서 목적지와 최종 전송 내용을 확인할 수 있어야 한다.

#### RAG 기반 보고 대상 탐색

목표는 **직원이 평소 쓰는 말로 적으면 실제 업무 문서와 완료 기준을 찾아 보고 양식을 완성하는 것**이다. 검색 결과를 이용해 사용자가 말하지 않은 완료 사실이나 진행률을 만들어내는 기능이 아니다.

입력 예: `협업 시연 로그인 화면은 끝났고 에러 문구 확인은 아직 하는 중이야.`

| 입력 표현 | 실제 연결 예 |
|---|---|
| 협업 시연 | 팀 협업 시연 프로젝트 |
| 로그인 | 로그인 기능 구현 업무 문서 |
| 로그인 화면은 끝났고 | 로그인 화면 구현 → 완료 |
| 에러 문구 확인은 아직 하는 중 | 오류 메시지 검수 → 진행 중 |

탐색 순서:

1. 원문을 업무별 구절과 상태 표현으로 분리한다. 부정·예정·진행 중을 구분하고 원문 구절을 근거로 보존한다.
2. 사용자가 접근 가능한 연결 프로젝트와 업무를 후보 범위로 정한다. 프로젝트가 명시되면 그 안에서 찾고, 생략되면 접근 가능한 연결 프로젝트를 대상으로 찾는다. 보고 목적지 채널이나 최근 프로젝트만을 근거로 범위를 잘못 고정하지 않는다.
3. 프로젝트명·업무 문서명·완료 기준·업무 설명에 이름 및 키워드 검색과 RAG 의미 검색을 함께 적용한다. 문서 본문 검색 결과가 실제 관리 대상 업무인지 확인한다. 일반 지식 문서나 과거 보고에 등장한 이름을 수정 대상으로 바로 취급하지 않는다.
4. 본인 담당 업무와 현재 개인 대화방의 최근 문맥을 순위에 활용한다. 문맥은 사용자별로 분리하고, 사용자가 명시한 프로젝트·업무보다 우선하지 않는다. 약칭이나 띄어쓰기 차이뿐 아니라 표현이 다른 완료 기준도 후보로 찾는다.
5. 후보의 최신 Outline 원문·권한·완료 기준 ID를 조회해 연결을 확정한다. RAG가 반환한 옛 내용이나 AI가 생성한 ID를 그대로 변경 대상으로 쓰지 않는다.
6. 명확한 후보는 바로 초안에 넣고, 비슷한 후보가 여럿이면 해당 부분만 선택하게 한다. 후보 없음·검색 실패·색인 준비 중을 구분한다. 검색 실패를 새 업무 생성 근거로 삼지 않는다.
7. 초안에서 연결된 업무명·기준명과 원문 해석을 확인·수정할 수 있게 하고, 실제 변경은 `보고 및 반영` 뒤 채널을 선택했을 때만 실행한다.

구현 규칙:

- 검색 결과는 자유 형식 답변만 반환하지 말고 프로젝트 ID·문서 ID·기준 ID, 제목, 근거 구절, 원문 revision, 검색 경로를 포함한 구조화된 후보로 전달한다. 기존 문서 답변 API와 별도 탐색 동작을 두거나 공통 검색 계층을 재사용한다.
- 의미 검색 유사도 하나만으로 자동 연결하지 않는다. 후보 간 차이, 명시한 이름, 기준 일치 여부, 사용자 문맥을 함께 검증하고 기준은 테스트 사례로 조정한다. 모델이 스스로 말한 신뢰도를 승인 근거로 삼지 않는다.
- 사용자에게 노출하거나 모델에 전달하기 전에 후보 권한을 검사한다. 조회 가능한 후보와 실제 수정 가능한 항목을 구분하고 반영 시 수정 권한을 다시 검사한다.
- 새 업무 생성 성공 후 반환된 문서로 Workhub 업무 목록을 즉시 갱신하고, 다음 보고에서 해당 업무를 직접 조회·연결할 수 있게 한다. 벡터 색인이 끝날 때까지 기다려야 새 업무를 찾는 구조로 만들지 않는다. RAG 갱신도 함께 예약한다.
- RAG가 준비 중이거나 일시 실패한 경우 최신 업무 목록의 이름·키워드 탐색을 이용한다. 그래도 모호하면 후보 선택으로 진행한다. 이 경로를 ‘RAG 검색 성공’으로 기록하지 않는다.
- 보고용 후보 검색의 범위와 2번 지식 질의의 검색 범위를 구분한다. 지식 검색용 컬렉션을 찾았다는 이유로 Workhub 업무 프로젝트로 자동 등록하지 않는다.

검증 데이터에는 정확한 이름, 약칭, 오타, 바꿔 말한 기준, 프로젝트 생략, 최근 대화와 다른 프로젝트, 같은 업무명, 여러 업무 혼합, 권한 없는 후보, 실제 미등록 업무, 신규 생성 직후 재보고를 포함한다. 후보 검색 성공과 최종 ID 연결 정확도를 따로 평가한다. 잘못된 업무 자동 연결은 필수 실패 항목이다.

#### 미등록 업무 생성 규칙

1. **생성 판단:** 접근 가능한 해당 프로젝트의 실제 업무를 조회한 뒤 새 업무 여부를 판단한다. 색인 누락·권한 부족·조회 실패·이름 모호성을 ‘없는 업무’로 간주하지 않는다. 유사한 기존 업무가 있으면 선택지를 제시한다. 다른 사용자에게만 보이는 문서의 존재나 제목은 노출하지 않는다.
2. **생성 시점:** 초안에는 생성 계획만 저장한다. `보고 및 반영` 뒤 목적지 채널을 선택했을 때 게시와 생성·상태 반영을 실행한다. 이미 명확한 내용을 별도 등록 화면에 다시 입력시키지 않는다.
3. **저장 위치:** 이미 연결된 프로젝트의 `업무 목록` 바로 아래에 개별 업무 문서로 게시한다. 새 프로젝트·컬렉션을 이 과정에서 자동 생성하지 않는다. 프로젝트가 없거나 불명확하면 기존 등록 흐름이나 프로젝트 선택으로 안내한다.
4. **문서 형식:** 사람용 업무 템플릿을 사용한다. 업무명, 담당자, 날짜, 상태, 업무 내용, 완료 기준, 보고 기록을 현재 파서가 인식하도록 작성한다. 완료 기준의 체크 여부와 `상태: 진행 중` 표기는 현재 사람용 형식을 따른다.
5. **필수 정보:** 업무명과 최소 1개의 구체적 완료 기준이 있어야 한다. 원문에서 추출하고 부족한 부분만 질문한다. 입력에 없는 완료 기준·마감일을 만들어내지 않는다. 담당자는 본인 보고이면 보고자를 기본값으로 미리 보여주고, 다른 담당자를 명시한 경우 기존 배정 권한을 검증한다.
6. **날짜·초기 상태:** 날짜가 없으면 사람용 템플릿의 `미정`을 사용한다. 보고 시각을 업무 시작일로 추측하지 않는다. 생성 직후부터 보고한 완료·진행 중·예정 상태를 반영하고 기존 집계 규칙으로 상태·진행률을 계산한다. 모두 예정인 빈 업무를 먼저 만들고 성공으로 반환하지 않는다.
7. **생성 권한:** 현재 `outline.create()`는 완료 기준을 포함한 생성에 관리자 제한이 있으므로 그대로 연결하면 일반 직원 흐름이 막힌다. 이번 구현에서는 **접근 및 문서 생성 권한이 있는 프로젝트에서 본인 업무와 본인에게 배정된 완료 기준을 생성하는 범위**를 지원하도록 서버 검증을 개편한다. 타인 배정·타인 업무 변경·프로젝트 등록 권한을 함께 확장하지 않는다. 봇의 서비스 계정 권한만으로 생성을 허용하지 않는다.
8. **재확인·중복 방지:** 생성 직전 접근 가능한 기존 업무를 다시 확인한다. 초안 작성 후 같은 업무가 생겼다면 기존 연결 여부를 확인한다. 같은 생성 요청의 재시도는 저장한 요청 ID·문서 ID로 복구하며, 제목이 같다는 이유만으로 생성 성공을 판단하지 않는다.
9. **기존 업무의 새 기준:** ‘없는 업무 추가’와 ‘기존 업무에 없는 완료 기준 추가’를 구분한다. 이번 요구만으로 기존 업무의 기준을 조용히 늘리지 않는다. 대응 기준이 없으면 기존 기준 선택 또는 별도 추가 요청으로 처리하고 해당 권한을 검증한다.

### 1.4 저장 상태와 실패 처리

다음 필드를 포함하는 통합 보고 저장 모델을 추가한다. 실제 테이블·클래스 이름은 기존 구조에 맞게 정한다.

| 구분 | 필요한 정보 |
|---|---|
| 보고 식별 | 보고 ID, 초안 버전, 작성자 계정, 생성 시각, 원문, 최종 보고문 |
| 채팅 문맥 | 요청 메시지 ID, 요청자와 봇의 개인 대화방 ID, 보고별 목적지 방 ID·종류, 필요 시 스레드 ID. 목적지는 선택 전 비어 있을 수 있음 |
| 보고 목적지 | 매번 채널 버튼으로 선택. 초안별 확정 목적지를 저장하고 실행 시 권한 재확인 |
| 연결 내역 | 처리 종류(기존 수정/신규 생성), 프로젝트 ID, 기존 문서 ID·기준 항목 ID, 변경 전후 값, 연결 근거, 원문 revision |
| 탐색 근거 | 보고 원문 구절, 검색 범위, 후보 ID, 이름·키워드·의미 검색 경로, 선택 사유, 사용자 확인 여부. 권한 없는 후보는 저장·표시하지 않음 |
| 신규 생성 계획 | 생성 요청 ID, 부모 문서 ID, 문서명, 담당자, 날짜, 완료 기준·초기 상태, 확정할 문서 본문, 생성 결과 문서 ID |
| 전송 결과 | 처리 상태, 중복 실행 방지 키, Rocket.Chat 메시지 ID·링크, 오류 |
| 반영 결과 | 문서별 proposal ID 또는 생성 요청 ID, 처리 종류, 상태, 적용 revision, 결과 링크, 오류·제외 이유 |

- 전송 상태와 반영 상태를 분리한다. 예: 전송 `미전송/처리 중/전송 완료/실패/결과 확인 필요`, 문서별 반영 `대기/처리 중/완료/충돌/실패/제외`.
- 동일 버튼을 여러 번 누르거나 서버가 재시작되어도 같은 버전의 보고가 중복 게시·반영되지 않도록 한다. 화면 버튼 비활성화만으로 처리하지 않는다.
- 버튼은 작성자·보고 ID·버전·동작·목적지에 묶는다. 다른 직원이 누르거나 오래된 초안 버튼을 눌러도 새 초안이 실행되지 않아야 한다.
- 초안 수정은 버전을 올린다. 아직 실행하지 않은 변경 제안은 다시 생성한다. 이미 전송·반영한 기록은 보존하고 후속 수정 동작을 명시한다.
- Outline 반영 전 최신 문서와 권한을 다시 확인한다. 직접 편집·담당자 변경·항목명 변경이 있으면 원문을 덮어쓰지 않고 충돌을 보여준다.
- 여러 문서는 전체 사전 검증 후 문서별로 반영한다. 중간 실패 시 `2건 중 1건 완료, 1건 실패`를 표시하고 실패한 문서만 재시도한다. 이미 성공한 문서를 자동으로 되돌리지 않는다.
- 기존 수정과 신규 생성이 섞인 경우에도 같은 원칙을 적용한다. 생성 요청 전에 예상 문서 ID와 확정 본문을 영속화하고, 응답 유실 시 해당 ID의 문서를 조회해 생성 여부·본문을 확인한다. 복구 시 이미 생성된 문서를 다시 만들거나 타인의 후속 편집을 덮어쓰지 않는다. 판정 불가능하면 `결과 확인 필요`로 남긴다.
- 전송 요청의 응답만 유실된 경우 실제 게시 여부를 확인한다. 설치 버전에서 안정적인 중복 방지·조회 방식이 확인되지 않으면 `결과 확인 필요`로 남기고 무조건 다시 보내지 않는다.
- 한쪽이 실패해도 다른 쪽의 성공을 취소하거나 숨기지 않는다. `보고 완료 / Outline 반영 실패` 상태에서 반영만 재시도할 수 있어야 한다.
- 메시지 길이 제한을 넘으면 사용자에게 축약·분할을 안내한다. 현재 `say()`의 문자열 자르기로 보고가 조용히 누락되지 않게 한다.

### 1.6 완료 기준 및 시연

- [ ] 멘션 없이 통합 업무 비서 개인 대화방에서 입력·초안 확인·수정·전송·반영을 끝낼 수 있다. 초안과 처리 결과는 같은 개인 대화방에 남는다.
- [ ] 목적지를 개인 대화방에서 선택·변경하고 이전 선택을 재사용할 수 있다. 개인 대화방 ID와 보고 목적지 ID가 혼동되지 않으며 초안별 목적지가 유지된다.
- [ ] 목적지 미선택 상태에서도 초안 작성·Outline 반영이 가능하다. 채널 접근·게시 권한 또는 봇 전송 권한이 없으면 전송만 차단하고 초안을 보존한다.
- [ ] 한 번의 입력으로 서로 다른 업무 2개 이상을 통합한 초안이 나온다. 여러 프로젝트 입력도 처리한다.
- [ ] 정확한 이름 없이 약칭·일상 표현으로 적은 보고도 RAG와 이름·키워드 검색을 통해 실제 업무·완료 기준에 연결된다. 모호한 부분만 질문하며 잘못된 업무에 자동 연결하지 않는다.
- [ ] 신규 업무 생성 직후 색인이 완료되지 않아도 다음 보고에서 해당 업무를 찾는다. RAG 장애·색인 지연을 신규 업무 부재로 오인하지 않는다.
- [ ] `[업무목록]`에는 업무 문서명이, 굵은 업무명 아래 `1. 2. 3.`에는 완료 기준이 표시된다. 프로젝트명을 업무 대신 나열하지 않는다.
- [ ] 완료·진행 중·예정이 원문 그대로 구분되며, 여러 업무의 번호가 각각 1부터 시작하고 언급하지 않은 기준은 변경되지 않는다.
- [ ] `보고 및 반영`을 누르면 매번 채널을 선택하고, 채널 선택 시 게시·업무 수정·신규 생성을 한 흐름으로 실행한다.
- [ ] 채널 선택 화면의 `뒤로 가기`는 게시·업무 반영 없이 초안으로 돌아간다. 이전 목적지로 자동 실행하지 않는다.
- [ ] 일반 직원이 본인에게 배정된 완료 기준을 가진 새 업무를 보고 흐름에서 추가할 수 있다. 새 문서는 사람용 템플릿으로 게시되고 초기 상태·집계·원문 보고를 보존한다.
- [ ] 없는 업무와 이름 모호성·조회 실패를 구분한다. 신규 업무의 정보 부족은 필요한 부분만 확인하고 타인 배정·권한 없는 생성은 차단한다.
- [ ] 기존 수정과 새 생성이 섞인 부분 실패, 생성 직전 같은 업무 등록, 생성 응답 유실·재시작·중복 클릭을 검증하고 문서가 중복 생성되지 않는다.
- [ ] 두 동작을 어느 순서로 해도 각각의 완료 상태가 정확하다.
- [ ] 사람용 템플릿과 기존 업무 형식 모두 본문·메모를 보존한다. 직접 Outline 체크와도 충돌하지 않는다.
- [ ] 동명이 업무, 미연결 항목, 타인 담당 항목, 오래된 버튼, 권한 철회를 처리한다.
- [ ] 중복 클릭, 재시작, 응답 유실, 여러 문서 중 일부 실패를 검증한다.
- [ ] 실제 직원 계정으로 개인 대화방에서 입력 → 수정 → 목적지 선택 → 전송 → 반영을 확인한다. 채널과 토론방을 각각 목적지로 선택해 최종 보고문 도착을 검증한다. API 테스트만으로 전체 시연 완료라고 기록하지 않는다.

시연은 `통합 업무 비서 개인 대화방 → 여러 업무의 진행 상황 입력 → 보고문 확인 → 보고 및 반영 → 채널 선택 → 완료 → 보고 보기·업무 보기`로 한다. 채널 선택의 `뒤로 가기`에서 변경이 없는지도 확인한다. 실제 사용자는 개인 대화방에서 모든 조작을 끝낼 수 있어야 한다. 보고 문장을 다시 복사하거나 업무별로 처음부터 입력하는 단계가 없어야 한다.

## 2. Outline 검색 기능 강화

### 2.0 확정한 진입점과 상세 구현 명세

2026-09-30 검색 진입점 결정 후 로컬 구현과 핵심 실행 검증을 진행했다. 기존 Outline 검색 화면의 AI 검색, Rocket.Chat 멘션 문서 검색, 대상·공개 범위 설정을 적용했다. 실제 시연 순서, 자동 검사 389건과 실서비스 확인 결과, 전체 타입 검사·운영 부하 등 남은 검증은 [구현·검증 결과](검색_기능_강화_구현_검증_결과.md)를 따른다. 다른 서버용 배포 묶음 적용이나 전체 운영 인수 완료를 뜻하지 않는다.

상세 작업 순서·데이터 계약·권한·UI·테스트·완료 기준은 [검색 기능 강화 구현 명세](검색_기능_강화_구현_명세.md)를 따른다. 아래 기존 검색 품질·자동 갱신 요구사항도 유효하며, 진입점은 이번 결정으로 대체한다. 충돌 시 2번에 한해 상세 명세의 확정 사항을 우선한다.

- **Outline:** 별도 검색 메뉴를 필수로 만들지 않는다. 기존 검색 화면의 검색창·필터 아래, 첫 문서 결과 위에 긴 설명 없이 `AI 검색` 버튼을 파란색으로 강조해 배치한다. 클릭하면 같은 영역에서 RAG 검색 결과와 근거 기반 답변을 제공하고 기존 문서 검색 결과는 유지한다.
- **Rocket.Chat:** 새 봇 대신 기존 `통합 업무 비서`를 사용한다. 봇이 참여한 채널·토론방에서 `@통합 업무 비서 프로젝트 A 설계 문서 링크 제공해줘`처럼 요청하면 문서 제목·링크를 우선 제공한다. 보고는 기존 개인 대화방 흐름을 유지한다.
- **공통:** 같은 검색 서비스·대상 레지스트리·권한 검사를 사용한다. 링크 요청은 불필요한 답변 생성을 생략하고, 의미 탐색·요약이 필요할 때 RAG·AI를 사용한다. 검색 요청으로 문서를 생성·수정하거나 보고를 전송하지 않는다.
- **현재 기반:** Outline 1.10.0 수정 소스와 프로젝트 관리용 서버 연결이 있다. 이는 검색 UI 구현 완료를 의미하지 않는다. 이미 적용된 프로젝트 관리 구조를 재사용하고 예전의 별도 Workhub 등록 화면을 다시 만들지 않는다.

### 2.1 목표와 현재 문제

**제목이 같은 문서를 찾는 수준을 넘어, 질문에 필요한 내용을 정확한 문서·시점과 연결해 답한다.** 문서가 존재하는데 검색 범위 밖이라 못 찾는 문제와, 내용을 찾았지만 잘못 요약하는 문제를 따로 해결한다.

앞선 실사에서는 선택 프로젝트 밖의 보고 문서를 찾지 못하거나, 일일 보고의 서로 다른 시각 내용을 섞고 불필요한 출처를 붙이는 사례가 있었다. 이는 이전 실행 환경의 관찰이며 모든 질문이 실패한다는 뜻은 아니다. 변경 전 동일 질문을 현재 버전에서 재현해 기준값을 남긴다.

검색 대상 관리도 이번 단계의 필수 범위다. 사용자나 관리자가 AI 개발자에게 매번 ‘이 프로젝트도 RAG에 추가해줘’라고 요청하지 않아도 되도록 한다. 현재 로컬 소스에는 Workhub 프로젝트 목록의 자동 전달과 등록 범위의 주기적 색인이 이미 있다. 이를 재사용하되 실행 중인 배포본·설정·실패 상태를 확인한다. 별도 설정 컬렉션과 실제 질의 범위는 구분되어 있으므로, ‘등록됨’을 ‘지금 모든 범위에서 검색됨’과 동일하게 표시하지 않는다.

### 2.2 사용 흐름

1. 직원이 기존 Outline 검색창에 검색어·질문을 입력한다. 일반 문서 검색 결과가 먼저 표시된다.
2. 검색창·필터 아래의 `AI 검색`를 누르면 같은 화면에서 RAG 검색을 실행한다. 입력 중 매번 AI를 호출하지 않는다.
3. 선택한 컬렉션·문서·작성자·시간 등 지원 필터와 현재 사용자 권한을 적용해 답변·근거 문서를 표시한다. 미지원 필터를 몰래 무시하지 않고 실행 전에 설명한다.
4. 짧은 검색어에는 관련 내용을 요약하고, 질문에는 해당 질문에 답한다. 답변 아래에서 추가 질문할 수 있으며 원문 링크를 제공한다.
5. 채팅 중에는 기존 봇을 실제 멘션해 문서 링크를 요청한다. 명확하면 짧은 링크 목록을, 애매하면 후보 선택을 제공한다. 채널 공개 권한을 확인할 수 없으면 요청자 개인 대화방으로 안내한다.
6. 근거가 없거나 검색 준비 중·조회 실패이면 서로 구분해 안내한다. 관련 조건·버전 차이와 기록 충돌을 숨기지 않는다.

Outline 전체 범위의 AI 검색은 `접근 가능한 검색 대상 전체`이며, 컬렉션 필터를 선택하면 그 범위로 좁힌다. Rocket.Chat에서 프로젝트를 명시하면 해당 범위, 명시하지 않으면 접근 가능한 검색 대상 전체를 사용한다. 개인 대화방의 마지막 보고 프로젝트를 채널 검색에 묵시적으로 적용하지 않는다. 일반 Outline 검색과 RAG 포함 범위의 차이를 표시한다.

`접근 가능한 검색 대상 전체`는 색인 대상으로 설정된 컬렉션과 사용자 권한의 교집합이다. 회사의 모든 Outline 문서가 자동 포함된다는 표현을 쓰지 않는다. 권한 없는 범위로 자동 확장하지 않는다.

공용 지식 컬렉션은 업무 프로젝트 등록과 분리해 검색 대상으로 설정할 수 있게 한다. 지식 검색만을 위해 모든 컬렉션을 Workhub 업무 프로젝트로 등록하게 만들지 않는다.

#### 검색 대상 자동 등록·갱신 흐름

| 상황 | 시스템 동작 |
|---|---|
| Workhub에서 프로젝트 연결 | RAG 검색 대상에 자동 포함하고 초기 색인을 예약한다. 별도 RAG 추가 요청은 필요 없다. |
| 연결된 프로젝트에 업무·문서 생성 또는 수정 | 변경을 감지해 자동 색인·갱신한다. |
| 보고에서 새 업무 생성 | 즉시 업무 탐색 대상으로 사용하고, RAG도 갱신한다. 즉시 업무 조회와 비동기 색인 완료 상태는 구분한다. |
| Outline에 새 컬렉션 생성 | 관리 화면에서 자동 발견하여 표시한다. 발견만으로 프로젝트 연결이나 검색 포함을 실행하지 않는다. |
| 업무 프로젝트가 아닌 지식 컬렉션 | 관리자가 ‘AI 검색에 포함’을 설정하면 초기 색인과 이후 갱신을 자동 수행한다. |
| 문서 삭제·권한 변경 | 검색 결과에도 반영한다. 권한 철회는 색인 갱신을 기다리지 않고 조회 시 차단한다. |

관리 흐름은 `컬렉션 자동 발견 → 프로젝트 연결 또는 지식 검색 포함 설정 → 초기 색인 → 변경 자동 갱신`이다. 포함 설정 이후의 문서별 등록·갱신은 사람이 반복하지 않는다.

### 2.3 구현 요구사항

#### 검색 대상 관리와 색인 처리

- **관리 화면:** 현재 Outline 프로젝트 관리 연동을 활용해 관리자용 검색 대상 설정을 제공한다. 접근 가능한 컬렉션을 검색·페이지 조회하고 `프로젝트 연결됨 / 지식 검색 포함 / 미포함`과 색인 상태를 표시한다. 관리자만 검색 포함 정책을 바꾸며 서비스 계정에만 보이는 컬렉션 이름을 관리자 화면에 노출하지 않는다. 기존 프로젝트 관리 화면과 중복 등록 화면을 만들지 않는다.
- **안정적인 식별:** 컬렉션 ID를 기준으로 검색 대상을 저장한다. 이름 변경·동명 컬렉션이 등록을 깨뜨리지 않아야 한다. 기존 이름 기반 설정은 ID를 확인해 호환·이전하며 중복 등록하지 않는다. UI 정책과 환경 설정을 별도의 상충하는 원본으로 남기지 않는다.
- **포함 사유:** `Workhub 프로젝트 연결`과 `관리자 지식 검색 포함`을 독립적으로 저장한다. 두 사유가 있는 컬렉션을 한 번만 색인한다. 프로젝트 연결 해제 시 지식 검색 설정이 남아 있으면 검색을 유지하며, 마지막 포함 사유가 사라지면 즉시 질의 범위에서 제외한다. 어느 경우에도 Outline 원본을 삭제하지 않는다.
- **신규 컬렉션 발견:** 관리 화면 조회·새로고침과 백그라운드 주기 조회로 최신 목록을 확인한다. 포함 대상만 문서 본문을 색인하며, 발견 목록 갱신 때문에 모든 컬렉션을 무조건 색인하지 않는다.
- **변경 감지:** Workhub가 수행한 연결·생성·수정 성공은 갱신 작업을 바로 예약한다. Outline에서 직접 수행한 변경은 주기적 비교로 감지한다. 설치 버전에서 이벤트 연동을 지원하고 검증한 경우 가속에 활용하되, 누락 복구를 위한 주기 조회를 유지한다.
- **부분 갱신:** 문서 ID·revision/내용 버전으로 변경 문서만 갱신한다. 단순 색인 주기가 돌았다는 이유로 모든 문서를 재임베딩하지 않는다. 이전 동기화가 실행 중일 때 들어온 갱신 요청도 유실하지 않는다.
- **실패 복구:** 재시작 이후에도 미처리 작업이 재개되도록 저장하고, 재시도·중복 합치기를 지원한다. 업무 생성은 성공했지만 색인이 실패한 경우 `업무 추가 완료 / AI 검색 갱신 재시도 중`으로 표시하고 업무를 다시 만들지 않는다. 네트워크 실패나 불완전한 목록 조회를 문서 삭제로 해석하지 않는다.
- **삭제·이동·권한:** 보관·삭제 문서는 비활성화하고 문서 이동 시 새 소속과 포함 여부를 재평가한다. 검색 후보·모델 입력·최종 출처 단계에서 현재 권한을 확인한다. 권한 확인이 실패하면 해당 근거를 사용하지 않는다. 갱신 작업의 완료를 기다리며 접근이 철회된 내용을 제공하지 않는다.
- **질의 범위:** 색인 대상, 사용자 권한, 사용자가 선택한 검색 범위를 모두 적용한다. 전체 검색은 세 조건을 만족하는 문서를 대상으로 한다. 프로젝트 보고 매칭은 1번의 업무 탐색 규칙을 따른다.
- **상태 표시:** `미포함 / 검색 준비 중 / 사용 가능 / 일부 실패 / 갱신 중`과 마지막 성공 시각·대상 문서 수·실패 수를 보여준다. 초기 작업을 예약한 시점에 검색 준비 완료라고 표시하지 않는다. 재시도 기능은 내부 엔드포인트나 환경변수 편집 없이 사용할 수 있게 한다.
- **지연 검증:** 발견·업무 목록 반영·색인 완료 시간을 따로 측정한다. 실제 동기화 주기와 실패 시 동작을 기록한다. ‘자동 갱신’을 ‘모든 의미 검색 결과가 즉시 최신’이라고 설명하지 않는다.

#### 검색 내용과 답변 정확도

- **검색 범위:** 실제 색인 대상·최근 동기화·갱신 실패를 확인할 수 있어야 한다. `문서 없음`, `아직 색인되지 않음`, `조회 실패`를 구분한다.
- **문맥 보존:** 보고 날짜, 보고 시각, 프로젝트, 업무 제목과 그 아래 상태를 묶어 검색한다. `[9월 28일 : 9시]` 같은 일반 텍스트 시각도 문맥에 포함한다.
- **원문 구분:** 현재 본문, 보고 이력, 인용, 템플릿 예시를 구분한다. 예시의 완료 상태를 실제 업무 완료로 답하지 않는다.
- **시점 구분:** 현재 상태 질문은 최신 업무 원문을, 과거 질문은 해당 날짜·시각 근거를 사용한다. 문서 수정 시각과 본문 속 보고 시각을 혼동하지 않는다.
- **내용 탐색:** 정확한 제목, 일부 키워드, 표현이 다른 질문, 오류 메시지·코드 관련 질문을 각각 평가한다. 기존 검색 방식 중 유효한 부분을 유지한다.
- **근거 연결:** 답변의 각 주요 사실은 해당 부분을 뒷받침하는 문서와 연결한다. 관련 없는 문서를 출처 수를 늘리기 위해 붙이지 않는다.
- **최신성:** 문서 수정·보관·삭제·권한 변경 시 오래된 내용이나 출처를 계속 보여주지 않는다. 답변 직전에도 필요한 권한·revision을 확인한다.
- **권한:** 검색 후보, 모델 입력, 답변, 출처 제목·미리보기 모두 사용자 권한을 따른다. 관리자 서비스 자격증명을 사용하더라도 실제 요청자의 권한을 유지한다.
- **불확실성:** 서로 충돌하는 기록은 충돌을 보여준다. 해결됐다는 근거가 없으면 해결됐다고 답하지 않는다.
- **속도:** 검색과 생성 시간을 따로 측정한다. 정확도와 함께 평가하고 무조건 더 큰 모델·더 긴 문맥으로 해결하지 않는다.

첨부파일 OCR·이미지 이해·모든 파일 형식 검색은 별도 요구사항이다. 이번 단계에서는 지원되는 문서 본문과 메타데이터의 정확도를 먼저 확보한다.

### 2.4 검증용 질문 세트

변경 전 원문 snapshot, 질문, 사용자, 범위, 기대 사실, 허용 출처, 답하면 안 되는 내용을 고정한다. 아래 사례마다 표현을 바꾼 질문도 넣는다.

| 사례 | 기대 결과 |
|---|---|
| 문서 제목을 알고 찾기 | 해당 문서 링크와 필요한 내용 반환 |
| 제목 없이 본문 키워드로 찾기 | 관련 본문과 실제 문서 반환 |
| 같은 문서의 오전·오후 보고 질문 | 해당 시각의 상태만 답하고 다른 시각과 섞지 않음 |
| 현재 상태와 과거 상태 질문 | 각각 해당 시점의 근거 사용 |
| 프로젝트 A 오류 해결 사례를 B 직원이 질문 | 공유 허용된 지식 범위에서 원인·해결 방법·적용 조건·원문 반환 |
| 같은 오류 문구지만 환경이 다른 사례 | 차이와 적용 조건을 표시하고 동일 해결을 단정하지 않음 |
| 정답 문서가 다른 컬렉션에 있음 | 범위에 포함하면 찾고, 좁은 범위에서는 제한을 설명 |
| 정답이 없음 또는 기록이 충돌함 | 모른다고 답하거나 충돌을 명시 |
| 템플릿 예시와 실제 기록이 함께 있음 | 예시를 사실로 인용하지 않음 |
| 문서 수정·보관·삭제·접근권한 철회 | 변경을 반영하고 이전 내용·제목이 누출되지 않음 |

프로젝트 A/B 오류 사례는 검증용 문서로 만든다. 실제 회사에서 발생한 사건처럼 꾸미지 않는다. 먼저 4번 없이 수동으로 검증 문서를 준비하므로 단계 순서는 유지된다.

### 2.5 코드 변경 지점과 작업 순서

- Workhub 진입·범위: [assistant.py](../../unified-work-assistant/src/workhub/assistant.py), [search.py](../../unified-work-assistant/src/workhub/search.py), [bot.py](../../unified-work-assistant/src/workhub/bot.py), [projects.js](../../unified-work-assistant/src/workhub/static/projects.js).

- 대상 자동 등록·관리: [search.py](../../unified-work-assistant/src/workhub/search.py)의 `sync_registry`, [main.py](../../unified-work-assistant/src/workhub/main.py)의 동기화 루프·관리 API, [rag_service.py](../../unified-work-assistant/src/document-agent/rag_service.py)의 프로젝트 등록·색인 루프, [projects.js](../../unified-work-assistant/src/workhub/static/projects.js)의 관리자 설정. 별도 작업 상태 저장이 필요하면 기존 저장 계층을 확장한다.

1. 고정된 질문 세트로 현재 답변·출처·지연 시간을 기록하고, 실행 환경의 검색 대상 등록·자동 색인 경로를 확인한다.
2. 컬렉션 ID·포함 사유·권한에 따른 대상 관리와 관리자 설정을 구현한다.
3. 프로젝트 연결·새 문서·수정·삭제·이동의 자동 갱신, 상태 표시, 실패 복구를 검증한다.
4. 답변 실패를 `검색 범위 / 후보 검색 / 문맥 분할 / 답변 생성 / 권한·최신성`으로 분류하고 원인부터 수정한다. 검색 전체를 근거 없이 재작성하지 않는다.
5. Outline 기존 검색 화면에 안내·버튼·답변·출처·후속 질문을 통합한다. 일반 검색을 AI 대기에 묶지 않고 검색어·필터 변경 시 이전 요청과 표시를 분리한다.
6. Rocket.Chat 기존 봇에 멘션 문서 검색을 연결한다. 링크 요청·내용 질문을 구분하고 공개 가능한 답변만 원 질문의 스레드에 전송한다.
7. 같은 자료와 계정으로 재측정하고, 개발에 사용하지 않은 바꿔 묻기 질문도 검증한다. 실제 단계별 구현은 상세 명세의 순서를 따른다.
8. 기존 테스트 및 1번 보고 대상 탐색·신규 업무 재보고, Outline 프로젝트 연결·해제 흐름의 회귀를 확인한다.

### 2.6 완료 기준 및 시연

- [ ] 기존 Outline 검색 화면에 `AI 검색`가 표시되고 일반 검색·필터·정렬·문서 열기가 유지된다.
- [ ] 버튼 클릭 시 같은 화면에 답변과 실제 근거 링크가 나오며, 실패·취소·검색어 변경이 일반 검색을 막지 않는다.
- [ ] Rocket.Chat 채널과 토론방에서 실제 멘션으로 프로젝트 문서 링크를 찾고, 새로고침 후에도 답변이 보존된다.
- [ ] 멘션하지 않은 채널 대화에는 응답하지 않고, 검색 요청이 보고 초안·업무 수정으로 처리되지 않는다.
- [ ] 링크 요청은 필요 없는 긴 답변 생성을 생략하며 동명 프로젝트·문서 후보를 구분한다.
- [ ] 요청자의 Outline 권한과 채널 공개 가능 범위를 별도로 확인하고, 확인 불가 시 개인 대화로 안내한다.
- [ ] 프로젝트를 연결하면 설정 파일 편집·개발자 요청 없이 검색 대상으로 등록되고 초기 색인이 시작된다.
- [ ] 업무·문서 생성·수정은 자동 갱신되며, Outline 직접 작성과 보고에서 생성한 업무를 모두 검증한다.
- [ ] 새 컬렉션은 관리 화면에 자동 발견되고, 지식 컬렉션은 프로젝트 연결 없이 ‘AI 검색에 포함’을 켜고 끌 수 있다.
- [ ] 이름 변경·동명 컬렉션·프로젝트 연결 해제와 지식 검색 포함 유지·마지막 포함 사유 제거를 정확히 처리한다.
- [ ] 문서 삭제·보관·이동·권한 철회가 결과에 반영되고, 서비스 재시작·일시 장애 후 미처리 색인이 복구된다.
- [ ] 검색 준비·갱신·실패 상태와 실제 반영 시간을 확인할 수 있으며, 색인 실패가 업무 중복 생성을 유발하지 않는다.
- [ ] 검색 범위를 사용자가 이해하고 선택할 수 있다.
- [ ] 고정한 필수 질문에서 기대 사실·시점·출처가 모두 맞는다. 미통과 사례는 완료 처리하지 않고 제한으로 기록한다.
- [ ] 근거 없는 답, 권한 없는 문서 제목·내용 노출, 삭제 문서 인용이 없다.
- [ ] 변경 전후 정답 여부·근거 적절성·응답 시간을 비교한 결과를 남긴다. 검색 성공 HTTP 응답만으로 정답 처리하지 않는다.
- [ ] 다른 직원 계정이 공용 해결 사례를 찾는 흐름을 실제 화면에서 확인한다.

Outline 시연: 공유된 오류 해결 문서를 미리 준비 → 다른 프로젝트 직원이 기존 검색창에 증상 입력 → `AI 검색` → 해결 방법과 조건·원문 확인 → 후속 질문. 단순히 같은 관리자 질문에 다시 답하는 장면을 핵심 가치로 삼지 않는다.

Rocket.Chat 시연: 허용된 채널·토론방에서 `@통합 업무 비서 프로젝트 A 설계 문서 링크 제공해줘` → 스레드에 문서 링크 응답 → Outline 원문 열기. 동명 문서 선택과 비공개 문서의 개인 대화 안내도 확인한다.

자동 관리 시연: 프로젝트 연결 → 별도 RAG 등록 없이 검색 준비 상태 확인 → Outline에서 문서 생성·수정 → 자동 갱신 후 검색 결과 확인. 별도 지식 컬렉션은 관리 화면에서 발견 → ‘AI 검색에 포함’ → 다른 프로젝트에서 검색한다. 마지막으로 권한 철회 후 해당 사용자의 검색 결과에서 제목·내용이 사라지는지 검증한다.

## 3. Workhub 프로젝트 등록 기능 간편화

### 3.1 목표와 범위

**Outline 컬렉션을 Workhub 프로젝트로 연결하는 필수 설정을 쉽게 만든다.** 사용자는 컬렉션 ID, 내부 API, 데이터베이스 구조를 몰라도 된다.

현재 관리자 권한 규칙을 유지한다. ‘누구나 쉽게’는 사용성 요구이며 모든 직원에게 등록·권한 관리 권한을 부여한다는 뜻이 아니다.

### 3.2 목표 사용 흐름

1. 등록 권한이 있는 사용자가 `프로젝트 연결`을 누른다.
2. 기본 화면에서 `기존 Outline 컬렉션 연결`을 선택한다. 검색 가능한 컬렉션 목록을 보여준다.
3. 컬렉션 이름·원본 링크·연결 여부를 확인하고 하나를 선택한다.
4. `프로젝트로 연결`을 누른다. 기존 컬렉션을 선택했는데 이름을 다시 입력하도록 요구하지 않는다.
5. 완료 후 해당 프로젝트로 이동한다. `Outline에서 업무 작성`, `업무 현황 보기`를 바로 제공하고 `AI 검색 준비 중 / 사용 가능 / 일부 실패` 상태를 보여준다. 프로젝트 연결에 따른 RAG 포함은 자동이며 별도 등록 버튼을 누르게 하지 않는다.
6. 컬렉션이 없는 경우에만 보조 선택지인 `새 프로젝트 만들기`로 이름을 입력한다.

### 3.3 구현 요구사항

- 접근 가능한 컬렉션만 후보로 보여준다. 이름이 같아도 ID로 구분하고 원본 링크를 제공한다.
- 이미 연결된 항목은 `연결됨`과 이동 버튼을 보여준다. 숨겨져 있어서 ‘왜 안 보이는지’ 추측하게 하지 않는다.
- 목록 검색, 빈 결과, 불러오는 중, 접근 불가, 서버 오류를 구분한다. 목록이 길면 페이지 조회를 지원한다.
- 기존 연결에서 필요한 입력은 컬렉션 선택뿐이다. 현재 프로젝트 관리자 지정 규칙은 보존하고 별도 설명한다.
- 신규 컬렉션 생성은 기존 권한 범위를 유지한다. 연결했다는 이유로 회사 전체에 문서를 공개하거나 멤버를 자동 추가하지 않는다.
- 같은 요청을 다시 보내거나 같은 컬렉션을 동시에 선택해도 프로젝트가 중복되지 않아야 한다. 현재 프로세스 잠금뿐 아니라 실행 구성에서의 저장 일관성을 확인한다.
- 등록 성공, 업무 동기화 진행, 검색 색인 준비를 구분해 보여준다. 색인 때문에 등록 화면을 장시간 멈추게 하지 않는다.
- 2번의 컬렉션 자동 발견·검색 포함 설정·실패 재시도 기능을 연결 화면에 통합한다. 업무 프로젝트 연결과 지식 검색만 포함하는 선택지를 구분하고, 중복된 검색 대상 관리 화면이나 저장 정책을 새로 만들지 않는다.
- `업무 목록` 문서가 없을 때는 현재 생성 경로를 조사해 일관되게 처리한다. 필요한 구조를 새로 만들 경우 연결 동작의 설명에 포함하고 기존 동명 문서를 중복 생성하지 않는다. 단순 후보 조회에서는 문서를 만들지 않는다.
- 사용 안내는 기존 Outline 직접 작성 기능을 따른다: `업무 목록` 바로 아래 템플릿 적용 → 작성 → 게시 → 동기화.
- 기존 연결 해제·관리자 지정 기능은 유지한다. 화면 간소화를 이유로 Outline 원본 삭제 동작을 추가하지 않는다.

### 3.4 코드 변경 지점과 작업 순서

- 화면: [projects.js](../../unified-work-assistant/src/workhub/static/projects.js), [index.html](../../unified-work-assistant/src/workhub/static/index.html) 및 실제 연결된 스타일 파일.

- [ ] 기존 연결·새 생성이 명확히 구분되고, 이미 연결된 프로젝트를 다시 만들지 않는다.
- [ ] 비관리자 직접 API 요청과 접근 불가 컬렉션 연결이 차단된다.
- [ ] 중복 클릭·동시 요청·연결 후 동기화 실패가 원본 손상이나 중복을 만들지 않는다.
- [ ] 연결한 컬렉션에 사람이 템플릿 업무를 게시하면 기존 자동 인식이 유지된다.
- [ ] 1번 보고와 2번 검색이 연결된 프로젝트에서 정상 동작한다.
- [ ] 프로젝트 연결 한 번으로 검색 준비가 시작되고, 관리 화면의 상태·재시도로 진행을 확인할 수 있다. 별도 RAG 추가 요청이 필요 없다.

시연: 기존 컬렉션 하나 검색 → 연결 → Outline에서 업무 문서 게시 → Workhub 업무 현황 확인. 이미 있는 문서를 다시 복사하거나 새 시스템으로 옮기는 작업이 없어야 한다.

## 4. Rocket.Chat 대화 내용 기반 문서 생성

### 4.1 목표와 범위

**채팅에서 해결한 내용을 다시 손으로 정리하는 수고를 줄이고, 나중에 검색할 수 있는 Outline 지식으로 남긴다.** 1~3번 완료 후 시간 여유가 있을 때 진행한다.

처음부터 모든 대화를 자동 문서화하지 않는다. 사용자가 특정 시작점과 끝점 또는 한 스레드를 선택해 요청하는 방식으로 구현한다. 문서 초안 자동 생성과 최종 게시를 구분한다.

### 4.2 목표 사용 흐름

1. 프로젝트 A 담당자들이 채널/토론방에서 오류 원인과 해결 방법을 논의한다.
2. 담당자가 시작 메시지를 지정하고 `여기부터 대화 정리`를 요청한다. 메시지 메뉴 연동이 어렵다면 메시지 링크·답장 기반 명령을 사용한다.
3. 끝점을 지정하거나, 요청 시각까지로 범위를 고정한다. 대상 방, 시작·종료 시각, 메시지 수를 보여준다.
4. AI가 아래 형식의 문서 초안을 만든다. 초안은 요청자에게 제공한다.
5. 담당자가 제목·내용·저장 컬렉션을 확인하고 수정한 뒤 `Outline에 저장`을 누른다.
6. 문서 링크와 저장 결과를 제공한다.
7. 이후 프로젝트 B 직원이 2번 검색 기능으로 유사 증상을 질문하고 문서를 찾는다.

권장 문서 형식:

```text
제목: [오류/문제 이름] 해결 기록

## 발생 상황
영향 범위, 증상, 확인된 환경·버전

## 확인한 원인
확인된 내용 / 아직 추정인 내용

## 해결 방법
실제로 수행한 순서와 변경 내용

## 해결 확인
누가 무엇을 확인했는지, 미확인 사항

## 적용 시 주의 사항
다른 프로젝트에 적용할 조건과 한계

## 남은 작업
대화에서 합의한 후속 작업. 없으면 없음

## 원본 대화
방, 대상 기간, 주요 메시지 링크
```

### 4.3 구현 요구사항

- **수집 범위:** 한 방의 시작·종료 메시지 또는 선택한 스레드를 기준으로 한다. 포함 경계·시간대·정렬을 고정하며 이후 도착한 메시지는 자동 추가하지 않는다.
- **수집 완전성:** 페이지 조회, 스레드 원문·답글, 편집·삭제 메시지를 처리한다. 길이 제한 때문에 일부만 읽었다면 전체 요약이라고 표시하지 않는다. 과도한 범위는 줄이도록 안내한다.
- **원문 검토:** 문서화 전에 선택 범위를 다시 확인할 수 있다. 선택 후 중요한 원문 변경이 감지되면 재생성·검토를 요구한다.
- **사실 구분:** 제안, 시도, 성공 확인, 미해결 사항을 구분한다. ‘해보자’는 발언을 ‘해결했다’로 요약하지 않는다. 원인이 대화에 없으면 확인되지 않았다고 적는다.
- **사용자 권한:** 봇이 읽을 수 있다는 이유만으로 사용자가 읽을 수 없는 대화를 가져오지 않는다. 실제 요청자의 채널 접근 및 Outline 저장 권한을 검증한다.
- **공개 범위:** 비공개 채널 내용을 더 넓은 공용 컬렉션에 자동 게시하지 않는다. 초안·목적지 공개 범위를 표시하고, 조직의 공유 권한 안에서 승인된 내용만 저장한다. 1차 구현에서 넓은 범위 공유를 판정할 수 없으면 제한된 목적지를 사용한다.
- **기존 에이전트 연결:** 문서 초안·저장 도구를 재사용하되 실제 요청자 권한을 전달한다. 관리자 전용 화면의 권한을 직원 요청에 대입하지 않는다.
- **주입 방지:** 대화 안의 명령문은 정리할 자료다. 도구 실행·외부 전송·권한 변경 지시로 따르지 않는다.
- **출처:** 문서에는 대화 범위와 주요 메시지 링크를 남긴다. 출처 링크에 자격증명을 넣지 않는다. 독자가 원본 채널 권한이 없을 수 있음을 고려한다.
- **중복·실패:** 요청 ID와 저장 결과를 남겨 중복 클릭·재시작·응답 유실 시 문서가 중복 생성되지 않게 한다. 저장 실패 시 편집한 초안을 보존한다.
- **범위 제한:** 1차 구현은 새 문서 생성까지다. 기존 지식 문서 자동 병합, 자동 업무 생성, 모든 개인 DM 수집, 주기적 자동 게시를 추가하지 않는다.

### 4.5 완료 기준 및 시연

- [ ] 선택한 범위만 정리하고 범위 밖 대화·다른 방·후속 메시지를 섞지 않는다.
- [ ] 주장·추정·실행·해결 확인을 구분하고 근거 없는 원인·해결책을 쓰지 않는다.
- [ ] 초안 수정과 목적지 확인 후 저장되며, 작성자에게 문서 링크가 반환된다.
- [ ] 비공개 대화·접근권한 철회·저장 권한 부족·중복 저장을 검증한다.
- [ ] 다른 직원이 공유 허용된 문서를 2번 검색으로 찾아 실제 근거를 확인한다.

최종 시연: 프로젝트 A 오류 논의 → 시작·끝 선택 → 초안 검토·저장 → 프로젝트 B 직원이 증상으로 질문 → 기존 해결 문서·적용 조건 확인. 이 흐름 전체가 검증된 뒤에만 ‘대화가 회사 지식으로 축적되어 다른 프로젝트에서 재사용된다’고 보고한다.

## 단계별 검증과 인수인계

문서에 적힌 파일명은 시작 지점이다. 실제 실행 경로를 추적한 뒤 수정한다. 특히 웹 `/app.js`는 현재 `static/projects.js`를 제공하므로 사용하지 않는 옛 화면 파일만 수정하는 실수를 피한다.

검증은 단계에서 바뀐 동작과 실제 위험에 맞춰 수행한다.

- 1번: 기존 `test_confirmation.py`, `test_report_recovery.py`, `test_chat_ui.py`, `test_permissions.py`, `test_human_tasks.py` 등을 회귀 검증하고 보고 양식·채널 전송·본인 업무 생성·생성 응답 유실 복구·수정과 생성의 부분 성공 테스트를 추가한다. 기존 관리자 전용 기준 생성 테스트는 새 본인 생성 허용 범위를 반영하되 타인 배정 차단 검증은 유지한다.
- 1번의 RAG 탐색은 별도 고정 사례로 후보 검색·최종 ID 연결·모호성 질문·신규 업무 즉시 조회를 검증한다. 유사한 문서가 검색됐다는 사실만으로 정확한 업무 연결에 성공했다고 판단하지 않는다.
- 2번: 기존 `test_workhub_rag.py`, `test_rag.py`, `test_rag_integration.py`, `test_user_acl.py` 등을 활용하고 고정 질문 평가, 대상 자동 등록·포함 해제·변경 갱신·색인 실패 복구 검증을 추가한다.
- 3번: 기존 프로젝트·권한·연결 해제 테스트를 유지하고 중복 연결·후속 동기화·사용 흐름을 검증한다.
- 4번: 문서 워크플로 테스트를 유지하고 범위 수집·출처·권한·중복 저장 테스트를 추가한다.
