# 검색 기능 강화 구현·검증 결과

작성일: 2026-09-30

Outline 기존 검색 화면의 **AI 검색**, 기존 Rocket.Chat 봇의 **멘션 문서 검색**, 검색 대상 관리 기능을 구현하고 로컬 실행 환경에 적용했다. 실제 계정·브라우저·모델·채팅 전송으로 핵심 흐름을 검증했다. 운영 부하 검증과 전체 TypeScript 검사는 아래 제한 사항에 구분했다. 모든 명세 항목의 운영 인수를 완료했다는 의미는 아니다.

## 1. 구현 결과

| 기능 | 현재 동작 |
|---|---|
| Outline AI 검색 | 기존 검색창과 필터 아래 파란 `AI 검색` 버튼. 같은 화면에 답변·근거 링크·추가 질문 표시. 일반 검색 목록 유지 |
| 검색 취소 | 중단·검색어/필터 변경 시 이전 응답 표시 차단. 후속 질문은 선택한 컬렉션 범위 유지 |
| Rocket.Chat | 기존 `통합 업무 비서` 실제 멘션으로 채널·토론방 검색. 원 질문 스레드로 응답 |
| 링크 요청 | 명확한 제목은 생성 모델 없이 링크 제공. 필요한 경우 의미 검색 병행 |
| 채널 공개 | 관리자에게서 해당 채널–컬렉션 공개 허용을 받은 자료만 채널에 표시. 그 외는 요청자 DM으로 전달 |
| 업무 보고 호환 | 기존 개인 대화방 보고 유지. `문서 요약 완료`는 보고, `문서 찾아줘`는 검색으로 분기 |
| 검색 대상 | 연결된 프로젝트 자동 포함. 독립 지식 컬렉션은 Outline의 `검색 대상 설정`에서 포함 가능 |
| 자동 갱신 | 문서 변경을 주기적으로 감지. 현재 Outline 직접 수정 감지 주기는 300초. 관리 화면에 수동 `갱신 요청`도 제공 |
| 권한·최신성 | 실제 사용자와 Outline 기본 권한 정책 확인. 생성 전/결과 제공 전 권한 재검사. 수정·삭제·보관·이동된 문서의 오래된 결과 차단 |

검색은 읽기 전용이다. 기존 프로젝트 관리, 보고 문서 반영 흐름과 분리되어 있다. Outline의 공식 유료 AI 기능을 켠 것이 아니라 기존 자체 RAG를 연결한 것이다.

## 2. 바로 따라 할 시연

시연 자료는 `검색 시연 A`, `검색 시연 B` 컬렉션에 준비했다. 실제 장애 기록이 아닌 **시연용 사례**임을 문서에 표시했다. 팀장·홍길동·김철수 계정에서 볼 수 있는 공유 자료다. 지식 검색만을 위해 Workhub 업무 프로젝트로 등록하지 않았다.

### A. 다른 프로젝트의 해결 기록 재사용 — 첫 번째로 시연

1. 일반 직원 계정으로 [Outline 검색](http://outline.workhub.test/search)에 들어간다.
2. 검색창에 **`Docker DB 연결 오류`**를 입력한다. 프로젝트명이나 문서 제목을 먼저 알려주지 않는다.
3. 기존 문서 목록을 보여준 뒤 파란 **AI 검색** 버튼을 누른다.
4. 답변과 **DB 연결 오류 해결** 링크를 확인한다. 문구는 실행마다 조금 달라질 수 있다.
5. 링크를 열어 실제 원문과 비교한다. 원문에는 `DB_HOST=localhost`였던 원인, `DB_HOST=db`로 변경 후 재시작한 방법, 같은 Docker 네트워크라는 적용 조건이 있다.
6. 검색 화면의 추가 질문에 **`외부 데이터베이스에도 그대로 적용할 수 있어?`**를 입력한다. 외부 DB는 실제 서버 주소를 사용해야 한다는 원문 조건을 확인한다.

설명할 핵심: **“문서 제목을 모르는 다른 직원도 오류 증상으로 과거 해결 기록을 찾고, 자기 환경에 적용할 조건까지 확인합니다.”**

### B. 대화 중 문서 링크 찾기

1. [Rocket.Chat 시연 채널](http://rocketchat.workhub.test/channel/ai-search-demo)에 들어간다.
2. `@`를 입력하고 자동완성에서 **통합 업무 비서**(`report-bot`)를 선택한다. 표시 이름을 일반 글자로만 적으면 실제 멘션이 아닐 수 있다.
3. 다음 내용을 보낸다.

   ```text
   @report-bot 검색 시연 A 설계 문서 링크 제공해줘
   ```

4. 원 질문의 **스레드/답글**을 열면 `시스템 설계서` 링크가 나온다. 클릭해 Outline 문서를 연다.
5. 새로고침하거나 다른 직원 계정에서 같은 스레드를 열어 답변이 남아 있는 것을 보여준다.
6. 왼쪽 **AI 검색 시연 토론**에서도 같은 문장을 사용한다. 채널과 토론방 모두 확인했다.

공개 범위도 보여주려면 같은 채널에서 다음을 보낸다.

```text
@report-bot 검색 시연 B 작업 메모 링크 줘
```

`검색 시연 B`는 이 채널에 공개 허용하지 않았다. 채널에는 **검색 결과는 개인 대화방으로 안내했어요.**만 나오고, 통합 업무 비서 개인 대화방에서 링크를 받는다. 요청자의 Outline 열람 권한도 필요하다.

### C. 개발자에게 RAG 등록을 부탁하지 않고 관리

1. 팀장 계정으로 Outline 검색 화면에 들어간다.
2. **검색 대상 설정**을 누른다.
3. 컬렉션 이름으로 찾고 **AI 검색에 포함**을 선택한다. 프로젝트 연결은 필요 없다.
4. `검색 준비 중/갱신 중`에서 `사용 가능`으로 바뀌면 검색한다. 필요하면 **갱신 요청**을 사용한다.
5. 같은 설정 아래 **채팅방에 검색 결과 공개**에서 채널과 공개할 컬렉션을 선택한다. 공개 시 현재·미래 채널 참여자가 답변을 볼 수 있다.

`검색 시연 A`와 시연 채널의 공개 설정은 이미 되어 있으므로 첫 시연에서 설정 작업을 반복할 필요는 없다.

현재 실행 컨테이너와 최종 이미지 ID가 일치함을 확인했다. 최종 서비스 healthcheck는 정상이며 Ollama도 실행 중이다. 별도 권한 검사용 임시 컬렉션은 삭제했다. 시연용 A/B 문서와 채널·토론방만 사용 가능하게 남겼다.

기존 보고의 실제 **전송·반영**을 사용자 업무에 다시 수행하지는 않았다. 실제 데이터에서는 해석·사전 검사와 문서 불변을 검증했고, 전송·신규 업무·중복 반영은 격리된 자동 테스트에서 검증했다.

## 4. 속도와 필터

현재 로컬 PC, Qwen 4B, 소수 계정·소규모 시연 기준이다. 링크 측정에는 다른 검색 검증이 함께 실행된 구간도 포함된다.

- 명확한 링크 검색 5회: p50 **7.33초**, p95/최대 **12.45초**. 표본이 5개라 p95는 운영 성능을 대표하지 않는다.
- 같은 링크 2건 동시 요청: **6.75초, 6.94초**. 모두 생성 모델 호출 0회.
- 문서 에이전트 내부 링크 처리: 대략 **2초대**. 전체 시간에는 사용자 확인·중계·결과 조회가 포함된다.
- 실제 채팅 멘션→답글 감지: **10.26~12.55초**. 테스트의 5초 간격 조회 오차가 포함된다.
- 실제 내용 질문: 모델 최초 로딩을 포함한 실행 약 **30초**, 이후 실행 약 **14초**.
- 상세: 링크 측정 (`reports/search-latency-results.json`; 로컬 자료), 내용 질문 (`reports/search-live-results.json`; 로컬 자료).

따라서 명세의 링크 약 3초 목표는 **전체 응답 시간 기준 미달**이다. 생성 모델을 생략해도 사용자 확인·중계 비용이 남아 있다. 빠른 검색이라고 과장해 시연하지 않는다.

| 기존 검색 필터 | AI 검색 처리 |
|---|---|
| 컬렉션 | 선택한 컬렉션과 읽기 권한·검색 포함 범위의 교집합 |
| 문서 | 해당 문서 ID로 제한 |
| 작성자 | Outline 검색과 같은 `collaboratorIds` 기준 |
| 기간 | 문서 `updatedAt` 기준. 일/주/달/년 지원, 달/년은 달력 기준 |
| 제목에서만 찾기 | 제목이 맞는 후보로 제한. 그 문서의 본문을 답변 근거로 읽을 수 있음을 안내 |
| 게시됨 + 초안 | 게시된 문서만 검색함을 표시 |
| 초안·보관만 선택 | AI 검색 버튼 비활성화 및 필터 변경 안내 |
| 정렬 | 일반 결과 정렬 유지. AI를 자동 재호출하지 않음 |

## 5. 변경 지점과 실행 계약

- Outline: `Search.tsx`, `KnowledgeSearch.tsx`, `server/routes/api/workhubSearch.ts`, 라우트 등록. 관리 패치·`upstream.lock.json` 갱신.
- Workhub: `knowledge.py`, `knowledge_chat.py`, `main.py`, `outline_bridge.py`, `search.py`, `bot.py`.
- 문서 에이전트: `knowledge_search.py`, `rag_service.py`, `rag_sync.py`, `rag_store.py`, Dockerfile.
- 공개 프록시: `/internal/outline-search/` 직접 접근 차단.
- Outline API: `/api/workhub.search.{capabilities,catalog,include,sharing,refresh,submit,result,cancel}`.
- 신원: Outline 서버의 실제 로그인 사용자 또는 Rocket.Chat 실제 발신자를 사용. 내부 서명 검증. 브라우저가 보낸 이메일/관리자 표시로 권한 부여하지 않음.
- Outline 기본 권한 정책을 일괄 확인하는 `workhub.searchAccess`는 관리자 서비스 인증과 추가 HMAC을 모두 요구한다.
- 검색 작업: 사용자별 요청 ID, 제한된 작업 수, 결과 유효 시간 30분. 재시작 중이던 작업은 실패 안내 후 재검색. 오래된 결과의 재사용 시 현재 권한·버전 확인.
- 채팅: 기존 보고 큐와 검색 큐 분리. 정상 메시지 저장 API 및 원 메시지 기반 고정 응답 ID로 중복 방지. 재연결 시 최근 100개 중 10분 이내 요청만 복구 대상. 수정된 메시지 자동 재실행 안 함.
- 등록 정책: 컬렉션 ID 기준으로 프로젝트 포함 사유와 독립 지식 포함 사유를 합산. 기존 환경변수 컬렉션은 최초 실행 시 독립 포함으로 이전.

## 6. 남은 검증·적용 범위

1. **전체 TypeScript 검사는 완료하지 못했다.** 전체 upstream 타입 검사 중 Docker/WSL이 응답하지 않아 중단했다. Docker를 복구했고 이후 검사를 자원 제한 상태로 나누어 실행했다. 빌드, 변경 파일 lint, 실제 브라우저 검사는 통과했다.
2. 장시간 동시 사용, AI 생성과 보고가 겹치는 부하, 장애 주입·응답 유실의 모든 조합, 일반 검색이 이전보다 20% 이상 느려지지 않았는지에 대한 전후 통계는 운영 인수 전 별도 검증이 필요하다. 작은 시연 표본으로 운영 용량을 보장하지 않는다.
3. 이번 적용은 **로컬 환경**이다. `deployment/`의 다른 서버용 묶음은 갱신하지 않았다.
4. AI 답변은 매번 같은 문장을 보장하지 않는다. 시연에서는 원문과 핵심 사실·조건을 비교한다. 문서가 바뀌는 중이면 재검색을 안내할 수 있다.

## 7. 복구 지점

- 변경 전 백업: `backups/search-upgrade-20260930/`. 실행 설정에는 비밀값이 있으므로 외부 공유하지 않는다.
- 이전 이미지: `unified-work-assistant/{outline,workhub,document-agent}:before-search-20260930`.
